## 一、Git 分支策略（先定这个，其余都挂在它上面）

### 建议结构

```
后端 ruoyi-6x                          前端 plus-ui-6x
─────────────────                     ─────────────────
6.X-procurement   ← 生产分支（服务器跑的）   6.X-Vue        ← 生产分支（服务器跑的）
6.X-next          ← 开发主线（超前改动落这里）  6.X-Vue-next   ← 开发主线
```

### 规则

1. **生产分支只接受「修 bug + 必要小优化」**，保持随时可部署状态。服务器 deploy.sh 走 git pull，不改部署方式。
2. **`-next` 分支从当前生产分支拉出**，所有超前功能在 `-next` 上开发。每个功能尽量一个 feature 分支（`feat/xxx`），合入 `-next`；`-next` 上只保留「能跑通」的状态。
3. **发布节奏**：一批功能完成后，把 `-next` 合回生产分支 → 走正常 `deploy.sh` 部署 → 打 tag（如 `v6.1.0`）。合回前必须过一轮本地 Playwright 全链路。
4. **数据库策略（简化版）**：**本地只维护一套库 `ry-vue-6x`，`-next` 与生产分支共用，不再向服务器同步任何东西**——直到发布合并。纪律：
   - 所有表结构改动**只做加法**（新表、加列带默认值、新字典、新菜单），禁止改列名/删列/加 NOT NULL 无默认值——这样旧代码跑新库不会出问题，两分支共用一套本地库才成立；
   - SQL 幂等脚本留在 `-next` 分支随代码走，发布合并时服务器 `apply-sql.sh` 一次性执行排队的脚本；
   - 若某次发布确实涉及破坏性变更，再临时开 `ry-vue-6x-next` 库隔离（大概率用不上）。
5. **agents/ 目录**（AI 服务）在同一个外层仓库，前端后端都跟踪远程，agents 本身不部署到服务器、不受部署分支影响，直接在外层仓库 master 上提交即可。

### 一句话版本

> 生产分支 = 服务器现在跑的，只收补丁；`-next` = 偷偷摸摸干的活；本地一套库两分支共用（改动只做加法）；发布时代码合回、SQL 脚本由服务器一次性执行。

## 三、建议实施顺序（对齐后细化）

```
第 1 批（打地基）：G1 的字段类需求（固资标识、实际单价、明细折叠）+ 分支策略落地
第 2 批（AI 链）：付款截图识别（G1#2）—— agents 服务加新链路，复用发票识别基建
第 3 批（数据流）：发票上传独立（G2#6）→ 报销导出（G3#8）→ 台账资金流程（G3#9）
第 4 批（体验/硬件）：Excel 预览（G4#10）→ 扫码枪（G4#11）
第 5 批（外联）：泛微/云盘联动（G4#12，单独讨论）
```

理由：字段先行（所有后续功能都依赖固资标识和实际单价）；AI 链路独立可并行；导出和台账依赖前两批的数据；扫码枪和预览是锦上添花；联动最后。
