## 一、背景与本轮澄清

### 1.1 用户口径（2026-09-20 原话提炼）

- 备用金**属于项目的钱**，但**可以回笼**：更多人申请、或单人申请更多，都能让备用金变多。
- 更合理的理解：备用金 = **流动资金**（不是固定额度池）。
- 每个员工都有备用金（约一万），申请下来后钱给到采购部门使用；还钱时也是一万 → **倾向不记录「是谁的钱」**（待部门确认）。
- 钱款状态三态：**已采购未报销 → 已报销未汇款 → 已报销已汇款**。
- 采购通过 → 进入「已采购未报销」，**同时记录在项目处与备用金处**；**项目资金不会因为汇款变多**。
- 报销导出 → 记作「已报销未汇款」；报销结束、汇款完成 → 「已报销已汇款」。
- 报销在本系统是**辅助**：真实作用是产出报销材料（去财务走流程/发短信等），系统只做材料生成与状态跟踪。
- 资金管理**可见+可操作分配给「采购经理」角色**，后续分配。
- 流程：李老师忙，**现阶段跳过最高决策人节点，后续要加回来**。

### 1.2 范围

| 做 | 不做（本轮） |
|---|---|
| 资金双账本模型（项目 + 备用金池） | 备用金申请流程（OA 内申请一万）—— 见 §7 P3 |
| 采购申请资金状态机（三态） | 邮件发送报销包（原设计二阶段，继续预留） |
| 报销包生成（ZIP）+ 状态联动 | 归属两套体系合并（模板7值 vs sys_dept） |
| 流程跳过最高决策人 | BOM/合同等其他模块 |

## 三、资金模型设计（核心）

### 3.1 双账本：项目账本 vs 备用金池

这是整个设计的地基。**两本账互不影响，各自记各自的**：

```
┌──────────────────────── 项目账本（现有）────────────────────────┐
│  budget（预算） − used（已用） = remaining（剩余）              │
│  used = 所有 status=finish 的采购申请金额之和（自购 + 对公）      │
│  ✅ 回笼/汇款 不会 让 used 减少 → 「项目资金不会因为汇款变多」    │
└─────────────────────────────────────────────────────────────────┘

┌──────────────────────── 备用金池（新增）────────────────────────┐
│  advanced（累计拨入） − used（自购支出） + recycled（累计回笼）   │
│                                    = available（可用流动资金）   │
│  只对「自购」生效；对公采购不动池子                              │
│  更多人申请 / 单人申请更多 → advanced 变大 → 池子变大 ✅          │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 关键口径（必须先定死，否则两本账对不上）

| # | 口径 | 我的建议 | 依据 |
|---|---|---|---|
| K1 | 拨入备用金算不算项目已用？ | **不算**。拨入只是把钱挪到池子，不是消费 | 否则采购时会二次扣减，重复计数 |
| K2 | 自购采购扣不扣项目预算？ | **扣**（现状 checkBudget 已如此，不改） | 实际消费就是项目支出 |
| K3 | 对公采购扣不扣项目预算？ | **扣** | 同上 |
| K4 | 对公采购动不动备用金池？ | **不动** | 对公是公司直付，不经过员工备用金 |
| K5 | 回笼（汇款到账）影响谁？ | **只影响池子**（available 增加），项目 used 不变 | 用户明确要求 |
| K6 | 池子按什么粒度算？ | **按项目**（备用金属于项目的钱），同时保留「按人」明细视图 | 用户口径 + 「记录详尽展示另说」 |

### 3.3 资金流水表增强（`pms_fund_flow`，只加列，符合加法纪律）

| 新增列 | 类型 | 说明 |
|---|---|---|
| `title_type` | varchar(20) | 自购/对公，写流水时从申请单带入（**分账筛选的基础**） |
| `flow_scene` | varchar(20) | **advance**（拨入）/ **purchase**（采购支出）/ **recycle**（回笼） |
| `account_type` | varchar(20) | **project**（项目账本）/ **reserve**（备用金池）—— 决定这笔进哪本账 |
| `person_id` / `person_name` | bigint / varchar(64) | 谁的钱（仅 advance/recycle 用，**可空**，待部门确认是否要填） |
| `reimbursement_id` | bigint | 回笼流水关联的报销包（可空） |

流水语义对照：

| 场景 | flow_type | flow_scene | account_type | 触发时机 |
|---|---|---|---|---|
| 备用金拨入 | in | advance | reserve | 手动录入（采购经理）或未来备用金申请流程 |
| 自购采购支出 | out | purchase | reserve | 申请审批通过（自动，现有逻辑扩展） |
| 对公采购支出 | out | purchase | project | 申请审批通过（自动，现有逻辑） |
| 报销回笼 | in | recycle | reserve | 报销包「汇款确认」（自动） |

> **不建新表**：池子余额用**实时聚合流水**算（与现有 `calcUsedAmountByProject()` 同思路），避免双写不一致。等量大了再加汇总表。

### 3.4 采购申请资金状态机（挂在申请单上，不挂流水）

反思：状态是**单据属性**，流水只是事件记录。所以状态机放 `pms_procurement_request`：

```
                 审批通过(finish)                生成报销包              汇款确认
  [审批中] ───────────────────────► [已采购未报销] ──────► [已报销未汇款] ──────► [已报销已汇款]
   waiting                        purchased_unreimbursed  reimbursed_unpaid    reimbursed_paid
       │                                                                          │
       └── 驳回/作废 → 不进入资金状态                                              └── 终态
```

新增列 `fund_status varchar(32)`，字典 `pms_fund_status`。

**对公分支（待确认，§8 Q3）**：对公是公司直付、员工不垫钱，理论上不需要报销。两种处理：
- a. 对公审批通过后 `fund_status = not_applicable`（不适用报销），不进三态
- b. 对公也走三态（如果财务要求对公也要归档材料）

### 3.5 ⚠️ 状态触发点的一个纠偏（需你确认）

你说「报销**导出**就记作已报销未汇款」。但「下载 ZIP」是**可重复操作**（下载三次不该改三次状态），而「生成报销包」是一次性业务动作。

**建议**：
- **生成报销包**（点「生成报销包」并成功打包）→ 状态变 `reimbursed_unpaid`
- **下载**（重复下载 zip）→ **不改状态**
- 若你坚持"下载即视为已提交"，则需额外加「已提交」按钮区分，反而更绕

## 四、报销模块设计

### 4.1 定位

报销在本系统 = **材料生成器 + 状态跟踪器**，不是财务系统。产出物是给财务/中心采购专员的一包材料（Excel + 验收图 + 发票 PDF），后续走线下/邮件流程。

### 4.2 数据模型

沿用 `pms_reimbursement`，补状态与金额：

| 字段 | 变化 | 说明 |
|---|---|---|
| `status` | 扩为 packing/packed/sent/**paid** | paid = 已汇款（终态） |
| `amount` | **新增** decimal(18,2) | 报销金额（默认 = 关联申请金额之和，可改，支持部分报销） |
| `paid_date` | **新增** date | 汇款日期 |
| `paid_amount` | **新增** decimal(18,2) | 实际回笼金额（默认 = amount） |
| `paid_by` / `paid_by_name` | **新增** | 谁确认的汇款 |
| `file_url` | 复用 | ZIP 存 MinIO，回写地址 |
| `content_json` | 复用 | 记录包了哪些文件（申请/图片/发票清单） |

**1:N 问题**（§8 Q6）：若一次报销要含多张申请，需加子表 `pms_reimbursement_item`（reimbursement_id + request_id + amount）。加法改动，符合纪律。**我倾向先做 1:N**，因为真实场景是攒一沓一起报，1:1 会逼用户建 N 个包。

### 4.3 打包内容（沿用原设计 §8.4）

```
【自购】AI项目_06月07日_入职必需品_001.zip
├── 采购申请表.xlsx                 ← 复用现有 exportFormExcel（中心模板）
├── 验收图片/
│   ├── 明细1_商品名_验收图.jpg
│   └── ...
├── 发票/
│   ├── 明细1_商品名_发票.pdf
│   └── ...
└── 清单.txt（可选）                 ← 包内文件与明细对应关系
```

实现要点：
- 后端新增 `GET /procurement/reimbursement/download/{id}`（前端已在调，补上即可）
- ZIP 生成：验收图/发票 URL 从 MinIO 拉流（服务器 `127.0.0.1:9000`）打包，**或直接引用 MinIO 地址由前端打包**——建议后端做（一致性好，且能写 content_json）
- ZIP 存 MinIO 回写 `file_url`，下载走 MinIO 直链或后端流式返回（建议后端流式，避免大文件占 MinIO 空间；也可打包后存 MinIO 便于重复下载——**待你选**，§8 Q9）

### 4.4 报销与资金联动

| 动作 | 资金侧效果 |
|---|---|
| 生成报销包（packed） | 关联申请 `fund_status` → `reimbursed_unpaid` |
| 汇款确认（paid） | 关联申请 `fund_status` → `reimbursed_paid`；写一条 `in/recycle/reserve` 流水（金额=paid_amount）；**备用金池 available 增加**；项目 used **不变** |
| 报销包作废/删除 | 回滚申请 `fund_status` → `purchased_unreimbursed`，删对应回笼流水 |

### 4.5 谁能操作

| 操作 | 角色 |
|---|---|
| 生成报销包 / 下载 | 采购经理（新）+ admin；申请人是否可自助生成 → §8 Q10 |
| 汇款确认 | 采购经理 + admin（涉及资金，收紧） |
| 查看 | 采购经理 + admin（普通用户暂不可见，与资金管理一致） |

## 九、反思（我对自己这版设计的批判）

1. **最大的风险是两本账的口径**（§3.2 K1~K6）。如果 K1/K2 定错，项目已用金额和池子余额会互相污染，后面所有报表都不可信。所以 P1 第一步应该是**把口径写成文档给部门确认**，而不是先写代码。
2. **不要建「备用金余额表」**。我一度想建 `pms_reserve_account` 存余额，但那样就要双写（流水 + 余额表），一致性难保。改成实时聚合流水，和现有 `calcUsedAmountByProject()` 一致，简单可靠。数据量大了再加汇总表（那是优化，不是现在的事）。
3. **状态机放申请单，不放流水**。流水是事件（不可变），状态是单据属性（可变）。混在一起会导致"改状态要改流水"这种恶心操作。
4. **报销 1:1 是现状的技术债**。表结构决定了只能一张申请一个包，但真实业务是攒一沓报。现在改（加子表）比上线后改便宜得多——建议 P2 直接做 1:N。
5. **「导出即已报销」这个触发点有坑**（§3.5）。下载是可重复动作，用它当状态触发点会导致状态抖动。已建议改成"生成报销包"触发。
6. **我之前推荐 autoPass 跳过节点是错的**，已在 §6 纠正并记录，避免以后再踩。
7. **不过度设计的边界**：备用金申请流程（P3）、邮件发送（P3）、归属体系合并（不做）都明确推后。本轮只做「分账 + 状态 + 打包」三件事。
8. **顺带修历史坑**：`procurement:fund:edit` 无菜单、报销 download 接口缺失、v5 把资金菜单从 common_user 移除后无人可见——这三个都在 P1/P2 里一并解决，不留尾巴。
