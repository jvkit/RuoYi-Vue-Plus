## 一、本轮确认的决策（2026-09-20 答复）

| # | 问题 | 确认结果 |
|---|---|---|
| D1 | 备用金记不记「是谁的钱」 | **记**。谁提起申请就标记为谁的钱（= 申请单 create_by） |
| D2 | 额度怎么来 | **管理员配置，默认每人 1 万**（可改） |
| D3 | 拨入算不算项目已用 | **不算**。备用金侧任何操作都不影响项目资金 |
| D4 | 举例口径 | 采购物品 a 花 1000 → **项目资金 −1000**；报销完 → **影响的是备用金**（释放占用） |
| D5 | 对公 | **一旦选对公，就与备用金完全无关** |
| D6 | 回笼金额 | **一定等于**采购金额（无部分报销、无差额） |
| D7 | 一次报销的基数 | **1 次报销 = 1 笔采购申请**（申请内含多个商品明细）→ 保持 1:1，**不需要子表** |
| D8 | 汇款审批 | **无审批**，指派的管理人员统一操作 |
| D9 | 资金状态怎么改 | **初期由资金管理人员手动管控**：默认显示「已采购未报销」，可勾选为「已报销」，**一旦勾选不可回溯** |

## 二、修正后的资金模型（v3 → v4 的关键变化）

### 2.1 项目账本（不变）

```
budget（预算） − used（已用） = remaining（剩余）
used = 所有 status=finish 的采购申请金额之和（自购 + 对公 都算）
回笼/报销 不会 让 used 减少   ← D3/D4
```
现有 `checkBudget()` / `calcUsedAmountByProject()` 逻辑**完全不动**。

### 2.2 备用金账本（v4 重设计：额度 + 占用，不再是拨入/回笼流水池）

v3 我设计的是「拨入 − 使用 + 回笼 = 可用」的流水池。D1/D2 确认后，模型简化为**按人的额度占用制**：

```
每人一个备用金账户：quota（额度，默认 10000，管理员可配）

occupied（已占用）= Σ 自购申请金额，其中 fund_status ∈ {已采购未报销, 已报销未汇款}
available（可用） = quota − occupied

已报销已汇款 → 该笔不再计入 occupied（钱回来了，额度自动释放）  ← D4「报销完影响的是备用金」
对公申请 → 永不计入 occupied                                    ← D5
```

**为什么这样更好**（v4 反思）：
- 「回笼」不需要单独记一条流水——它天然等于「状态变为已报销已汇款后，占用自动释放」，聚合即得，无双写。
- 「单人申请更多 → 备用金变多」= 管理员把该人 quota 调大，语义直接对上，不需要"拨入"事件。
- 备用金侧完全不碰项目账本（D3），两本账彻底解耦。

### 2.3 是否还写「回笼」流水？—— 建议不写（待你点头，§10 Q1）

- 不写：池子数据全部由 `fund_status` 聚合得出，流水表只记采购支出（out），最简。
- 写：流水叙事更完整（钱出去、钱回来各一条），但**汇总时绝不能对流水求和算池子**（会重复计数），只能当审计日志看。
- **我倾向不写**（P1/P2），将来部门要看完整资金叙事再加（纯加法，不破坏）。

| 列 | 类型 | 说明 |

## 四、资金状态机（手动、单向、不可回溯）

```
                    审批通过(finish)                    资金管理员勾选「已报销」        资金管理员确认「已汇款」
   [审批中 waiting] ───────────────► [已采购未报销] ──────────────────────► [已报销未汇款] ────────────────► [已报销已汇款]
    （不进资金状态）              purchased_unreimbursed                reimbursed_unpaid              reimbursed_paid
                                        │                                     │                            （终态）
                                        └── 对公 → not_applicable ────────────┘（不进三态，见 §10 Q2）

   ⛔ 无任何回退路径（D9：一旦勾选为报销就不能回溯）
   ✅ 允许向前跳级：直接勾「已汇款」= 同时补 reimburse_date + paid_date（业务上钱回来了必然已报销）
```

规则：
- 触发**全部手动**，由资金管理人员（采购经理角色）在「资金状态管理」视图勾选，支持批量（D9/D10）。
- 每次变更写 `reimburse_by/paid_by` + 时间戳留痕（不可回溯 ⇒ 必须能查谁改的）。
- **报销包生成不自动改 fund_status**（v3 的自动联动取消）——报销模块只产材料，资金状态由人管控（D9/D10）。
- 备用金占用随状态自动变化：`已报销已汇款` 后该笔从 occupied 移除，额度自动释放（无需任何额外动作）。

## 五、报销模块设计（补完半成品）

### 5.1 定位（D10）

**材料生成器 + 展示**。产出 ZIP 给相关部门，系统不管财务流程本身。

### 5.2 必须补的实现（现状是空的，见探索记录 §四）

| 缺口 | 补法 |
|---|---|
| 无 ZIP 打包代码（采购模块内零命中；`setFileUrl` 全仓零命中） | 后端实现打包：采购申请 Excel（复用 `exportFormExcel`）+ 每条明细验收图 + 每条明细发票。工具用 **Hutool `ZipUtil`**（项目已依赖 hutool-bom 5.8.47），或参考 `ruoyi-gen/GenTableServiceImpl` 的 zip 写法 |
| `file_url` 永远空 | 打包后 ZIP 上传 MinIO，回写 `file_url`；`content_json` 记包内清单 |
| 无 `/download/{id}` 接口（前端已在调 → 404） | 新增 `GET /procurement/reimbursement/download/{id}` |
| 生成报销包只插记录 | 生成时即打包（status: packing → packed），失败要给出明确错误（如"该申请无验收单/无发票"） |
| 权限 `:edit`/`:remove` 无菜单 | 补菜单按钮权限 |

### 5.3 ZIP 结构（沿用原设计 `采购系统详细页面规划.md` 页面八）

```
【自购】AI项目_06月07日_入职必需品_001.zip
├── 采购申请表.xlsx           ← 中心模板导出（现有能力）
├── 验收图片/
│   ├── 01_商品名_验收图.jpg
│   └── ...
├── 发票/
│   ├── 01_商品名_发票.pdf
│   └── ...
└── 清单.txt                 ← 包内文件 ↔ 明细对应关系（便于财务核对）
```

- ZIP 文件名 = 申请标题 + 三位序数（与导出 Excel 命名规则一致）。
- 前提校验：申请 status=finish 且有验收单（原设计 §8.4 规则），不满足给明确提示而不是打空包。
- 素材来源：验收图/发票 URL 存在验收明细上，文件在 MinIO；后端拉流打包（服务器走 `127.0.0.1:9000`，本地同）。

### 5.4 ZIP 存哪儿（§10 Q3）

- 建议：**存 MinIO**（回写 file_url），重复下载快、可追溯；缺点是占空间（一包几 MB～几十 MB）。
- 备选：每次实时打包（不占空间，但每次都要拉 MinIO 素材，慢）。

## 十一、反思（v3 → v4 我改了什么、为什么）

1. **v3 的「拨入/回笼流水池」被 D1/D2 推翻了**。v3 假设备用金是一个靠"拨入事件"充值的池子；实际是"每人固定额度 + 采购占用 + 报销释放"。改成额度占用制后：不需要 advance/recycle 流水、不需要手工录入入口、`account_type`/`flow_scene` 列全省掉。**表变更从 5 列降到 3 列，页面少一个录入弹窗**——这是本轮最大的简化。
2. **v3 的"报销包生成自动改资金状态"被 D9 推翻**。你要的是人管控、不可回溯。所以 v4 把两者彻底解耦：报销包状态只管材料（packing/packed/sent），资金状态只在申请单上由人勾选。**避免两个真相源**是这里最重要的设计约束。
3. **v3 的 1:N 子表不需要了**（D7 明确 1:1）。省一张表、省一套级联逻辑。
4. **v3 的 `paid_amount` 可编辑不需要了**（D6 回笼一定等于采购金额）。少一个可能填错的输入。
5. **不可回溯 ⇒ 必须留痕**。v4 因此加了 `reimburse_by/paid_by` + 时间戳（v3 只在报销表上有 paid_by）。这是"业务上不能随便改"的技术兜底：改错了不能回退，但至少能查到谁改的、什么时候改的。
6. **仍然坚持不建余额表/不存 occupied 列**。额度是配置（存），占用是事实（算）。存了就要双写，早晚对不上账。
7. **风险点**：`fund_status` 的存量回填要一次做对（已 finish 的自购单全部置"已采购未报销"），否则上线后资金看板数字是错的，而状态又不可回溯 → 错了很难修。所以 P1 的 SQL 里回填语句要单独 review，并且**先在本地库跑一遍看数量对不对**。
8. **顺带清掉的三个历史坑**：报销 download 接口缺失（前端必 404）、`procurement:fund:edit` 无菜单、`procurement:reimbursement:edit/:remove` 无菜单。都在 P1/P2 内解决。
