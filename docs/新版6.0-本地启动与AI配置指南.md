## 0. 这套系统由哪几部分组成

新版（6.0.0）是前后端分离 + 独立 AI 后端的架构，一共 5 个常驻组件：

| 组件 | 是什么 | 端口 |
|---|---|---|
| MySQL | 数据库（存业务数据） | 3306 |
| Redis | 缓存（登录态、验证码、分布式锁等） | 6379 |
| **主后端** `ruoyi-6x` | Spring Boot 主程序（登录、菜单、业务接口） | 8088 |
| **AI 后端** `ruoyi-snailai-server` | 独立的 AI 服务（智能体、模型、聊天） | 8900 |
| **前端** `plus-ui-6x` | Vue3 页面（浏览器访问） | 8082 |

浏览器打开的是前端 8082；前端通过代理把接口转发给后端 8088；8088 里的 SnailAI 客户端再连到 AI 后端 8900。

```
浏览器(8082) ──> 前端 ──代理──> 主后端(8088) ──gRPC──> AI后端(8900)
```

## 1. 先说最重要的概念：什么叫"打进 jar"

### 1.1 Java 程序是怎么跑起来的

Java 项目写完源码（`.java` 文件）后，不能直接运行，要经过"编译 + 打包"变成一个**可执行的 jar 文件**。

- **jar** 说白了就是一个压缩包（类似 zip），里面装着：
  - 编译好的 Java 字节码（程序本体）
  - **配置文件**（`application.yml`、`application-dev.yml` 这些）
  - 依赖的第三方库
- 运行时用 `java -jar xxx.jar` 一次性把整个包加载起来。

### 1.2 "打进 jar" 到底指什么

打包命令（Maven）在执行时会**把 src 下的配置文件复制进 jar**。所以：

```
你改源码里的 application-dev.yml  →  只是改了磁盘上的文本文件
               │
               │  （必须重新打包）
               ▼
    mvn package  →  把新配置"打进"新的 jar
               │
               ▼
    java -jar 新.jar  →  运行时读到的才是新配置
```

**结论：改完配置文件，必须重新 `mvn package` 打包，新配置才会生效。**

### 1.3 绕开"重新打包"的办法：命令行参数

除了重新打包，还有第二种改配置的办法——**启动时用命令行参数临时覆盖**：

```bash
java -jar app.jar --配置项=新值
```

例如：
```bash
java -jar app.jar --server.port=8088
```
就等于临时把 `server.port` 改成 8088，**不需要重新打包**。但注意：这只是本次启动有效，下次重启不带这个参数就又变回 jar 里的默认值了。

> 我们这次遇到的坑就是这样：我改了源码里的 `snail-ai.enabled: true`，但没重新打包，
> 运行的 jar 里还是 `false`，所以 AI 客户端一直没启动。后来用命令行参数
> `--snail-ai.enabled=true` 覆盖，才真正生效。

## 2. 前置环境（装一次即可）

新版后端需要 **Java 21**，而系统默认是 Java 17，所以用 sdkman 单独装了 JDK 21。

```bash
# sdkman 是管理多个 Java 版本的工具，装在用户目录 ~/.sdkman，不碰系统
# （下面这几条只在第一次安装时执行）

curl -s "https://get.sdkman.io" | bash          # 安装 sdkman
source "$HOME/.sdkman/bin/sdkman-init.sh"        # 让 sdkman 生效

sdk install java 21.0.12-tem                      # 装 JDK 21（Temurin）
sdk default java 21.0.12-tem                      # 设为默认
```

验证：
```bash
java -version   # 应显示 21.x
```

## 3. 启动数据库（MySQL + Redis）

数据库和缓存是容器（Docker）跑的。容器平时是"停止"状态，用 `docker start` 拉起来：

```bash
docker start mysql redis
```

验证：
```bash
docker ps | grep -E 'mysql|redis'
# 应看到两个容器处于 Up 状态
```

> MySQL 里有两个库：
> - `ry-vue`：**生产老库**（5.6.2 用的），我们**不动它**。
> - `ry-vue-6x`：**新版专用库**，新版后端和 AI 后端都连这个。
> 之所以分开，是因为 6.0.0 的表结构和老版不一样，直接共用会报错（比如缺列）。

## 4. 新版后端（ruoyi-6x）：构建 + 启动

### 4.1 构建（打包成 jar）

```bash
cd /home/jvkit/workspace/oa/ruoyi-6x

export JAVA_HOME="$HOME/.sdkman/candidates/java/current"
export PATH="$JAVA_HOME/bin:$PATH"

./mvnw -DskipTests package
```

- `mvnw` 是 Maven 的 wrapper（自动下载合适的 Maven 版本），等价于 `mvn`。
- `-DskipTests` 跳过测试，加快打包。
- 第一次会下载大量依赖，较慢（约 2~3 分钟）。
- 成功后在 `ruoyi-admin/target/` 下生成 `ruoyi-admin.jar`。

### 4.2 启动主后端

```bash
cd /home/jvkit/workspace/oa/ruoyi-6x/ruoyi-admin

export JAVA_HOME="$HOME/.sdkman/candidates/java/current"
export PATH="$JAVA_HOME/bin:$PATH"

nohup java -jar target/ruoyi-admin.jar \
  --server.port=8088 \
  --snail-ai.enabled=true \
  "--spring.datasource.dynamic.datasource.master.url=jdbc:mysql://localhost:3306/ry-vue-6x?useUnicode=true&characterEncoding=utf8&zeroDateTimeBehavior=convertToNull&useSSL=true&serverTimezone=GMT%2B8&autoReconnect=true&rewriteBatchedStatements=true&allowPublicKeyRetrieval=true&nullCatalogMeansCurrent=true" \
  > /tmp/ruoyi-6x-admin.log 2>&1 &
```

逐段解释这些参数：
- `nohup ... &`：让程序在后台运行，关掉终端也不停。
- `> /tmp/xxx.log 2>&1`：把日志写到文件，方便查看。
- `--server.port=8088`：端口用 8088（默认 8080 被别的程序占用）。
- `--snail-ai.enabled=true`：**关键**，开启 SnailAI 客户端模式（否则 AI 聊天没客户端实例，报"没有可用的客户端实例"）。
- `--spring.datasource...url=...`：把数据库指向 `ry-vue-6x`（默认配置指向老库 `ry-vue`，我们不用）。

> **每次重启后端，这三个参数都要带上**，否则端口会回 8080、AI 客户端不启动、连错数据库。

验证启动成功：
```bash
sleep 40
ss -ltnp | grep ':8088'        # 应看到监听
grep 'Started DromaraApplication' /tmp/ruoyi-6x-admin.log
```

## 6. 前端（plus-ui-6x）：安装依赖 + 启动

### 6.1 安装依赖（第一次）

```bash
cd /home/jvkit/workspace/oa/plus-ui-6x
pnpm install
```

### 6.2 启动开发服务器

```bash
cd /home/jvkit/workspace/oa/plus-ui-6x
nohup pnpm dev --port 8082 > /tmp/plus-ui-6x-dev.log 2>&1 &
```

- `--port 8082`：指定端口（配置里默认是 80，被系统 nginx 占用，所以用 8082）。
- 启动后浏览器访问 `http://localhost:8082`。

### 6.3 前端代理（vite.config.ts）

前端把请求代理给后端，靠的是 `vite.config.ts` 里的 proxy 配置。我们改了一处：

```ts
proxy: {
  [env.VITE_APP_BASE_API]: {
    target: 'http://localhost:8088',   // 原来是 8080，改成 8088
    changeOrigin: true,
    ws: true,
    rewrite: path => path.replace(new RegExp('^' + env.VITE_APP_BASE_API), '')
  }
}
```

意思是：所有以 `/dev-api` 开头的请求，转发到 `http://localhost:8088`（主后端），并去掉 `/dev-api` 前缀。

> 注意：`.env.development` 里设了接口加密 `VITE_APP_ENCRYPT=true` 和后端 `api-decrypt` 对齐，
> 不要随意改。端口我们是用 `--port` 参数覆盖的，没改 `.env` 文件（那文件含密钥，也不建议改）。

## 8. AI 模型是怎么配进去的（company 三个模型）

AI 后端里的模型存在数据库表里（`ry-vue-6x` 库）：

- `sai_model_provider`：模型提供方（OpenAI、Claude、公司内网等）
- `sai_model_config`：具体模型（glm-5.2、deepseek-v4-pro、deepseek-v4-flash）

我们新增了一个提供方"公司内网"（指向 `https://chat.iphy.ac.cn/api/v1`），下面挂了三个模型。
每个模型的关键字段：
- `api_endpoint`：接口地址 `https://chat.iphy.ac.cn/api/v1`
- `api_key`：**加密存储**（SM4 国密算法加密），不是明文
- `adapter_key`：`openai-compatible`（OpenAI 兼容协议）
- `model_type`：`CHAT`（对话模型）

> 加密后的 key 长这样（举例）：`k0rILuwYVn24...`。如果以后在数据库里看到 key 不是明文，
> 是正常的——应用读取时会自动解密。
> 新增模型时如果直接手写 SQL，key 必须用同样的 SM4 加密（密钥/IV 见 AI 后端配置的
> `snail-ai.crypto`，默认值可从配置文件看到），否则应用解密不出来。

## 9. 常见坑与排查

| 现象 | 原因 | 解决 |
|---|---|---|
| 登录要验证码 | 6.0 dev 默认开验证码 | 正常，手填数学题答案 |
| 8088 起不来 | 端口被占 | 换端口或停占用进程 |
| AI 会话报"获取 AI 用户身份失败" | `/snail-ai` 没走对主后端 | 前端代理 `/snail-ai` 走 8088（勿直连 8900） |
| AI 会话报"没有可用的客户端实例" | 主后端 `snail-ai.enabled` 为 false（或改了配置没重新打包） | 启动带 `--snail-ai.enabled=true` |
| 模型报"apiKey is required" | 用的模型没配 key，或 key 没加密对 | 检查 `sai_model_config` 的 key |
| 改配置不生效 | 改的是源码，jar 里还是旧的 | 重新 `mvn package` 或命令行参数覆盖 |

## 10. 停止服务

```bash
# 停止主后端 / AI 后端（按进程名找 pid 再 kill）
ps aux | grep 'ruoyi-admin.jar' | grep -v grep
ps aux | grep 'ruoyi-snailai-server.jar' | grep -v grep
# 用 kill <pid> 停掉

# 停止前端
pkill -f 'vite serve --mode development --port 8082'

# 停止数据库容器（可选，不停止则保持运行）
docker stop mysql redis
```
