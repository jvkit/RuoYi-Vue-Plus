## 二、关键机制探索结论

### 2.1 Warm-Flow 角色审批 = 或签

**探索方式**：反编译 `warm-flow-core-1.8.5.jar` 的 `TaskServiceImpl.addTask`。

**结论**：
- 一个审批节点只会生成 **一个 Task 实例**。
- Task 的 `permissionList` 字段会保存该节点所有预设办理人（角色展开后的用户 ID 列表）。
- 办理时只要当前用户在该列表中即可办理，办理后任务结束。
- 因此，**多个用户绑定同一角色时，任意一人通过即可**，无需额外配置。

**影响**：需求 1 无需改动代码，只需在文档/用户手册中说明即可。

---

### 2.2 现有发票表可用

**探索方式**：查看 `ruoyi-modules/ruoyi-invoice/domain/InvoiceInfo.java`。

**结论**：
- 已有 `invoice_info` 表，字段包括：发票代码、发票号码、发票类型、金额、税额、价税合计、开票日期、销售方、购买方、状态、关联订单号、AI 审核意见、真伪状态等。
- 缺少本次需要的字段：
  - `acceptance_id`：关联验收单
  - `acceptance_item_id`：关联验收明细
  - `request_id`：关联采购申请
  - `project_id`：关联项目
  - `is_red` / `red_flag`：是否冲红
  - `valid_flag`：是否有效（多传/重复的发票标记为无效）
  - `invalid_reason`：无效原因（重复、未匹配、多页等）
  - `ocr_json`：OCR 原始结果
  - `pdf_url`：PDF 文件地址

## 三、详细设计方案

### 3.1 角色与权限体系

#### 角色改名清单

| 原角色 key | 原角色名 | 新角色名 | 说明 |
|---|---|---|---|
| team_leader | 团队上级 | **CEO** | 流程中改名为 CEO |
| dept_leader | 部门上级 | **最高决策人** | 流程中改名为最高决策人 |
| warehouse_admin | 仓库管理员 | 仓库管理员 | 不变 |
| common_user | 普通用户 | 普通用户 | 不变 |

#### 账号调整

- **李迪（lidi）**：额外绑定 `admin` 角色，拥有超级管理员权限。
- **老师**：如需专属账号，可新建用户并绑定 `admin` 角色；也可以直接使用 admin 账号。

#### 普通用户可见菜单

给 `common_user` 角色绑定以下菜单（只给 query 权限，工作流只给 query）：

- 首页
- PRIME AI
- 我的任务
- 手机端专属
- 采购管理 → 采购申请
- 采购管理 → 采购验收
- 采购管理 → 仓库库存
- 采购管理 → 领用申请
- 工作流（只读，只给 query 权限）

#### 操作权限规则

| 单据状态 | 自己能否编辑 | 自己能否删除 | 别人能否编辑 | 别人能否删除 |
|---|---|---|---|---|
| 草稿 / 未提交 | ✅ | ✅ | ❌ | ❌ |
| 审批中 | ❌ | ❌ | ❌ | ❌ |
| 已通过 / 已完成 | ❌ | ❌ | ❌ | ❌（仅 admin 可删除/作废） |

### 3.2 采购申请流程更新

#### 新流程

```
提交申请 → 项目负责人审批 → CEO 审批 → 金额网关分支：
  ├─ 金额 < 1000 元 → 结束
  └─ 金额 ≥ 1000 元 → 最高决策人审批 → 结束
```

#### 节点调整

1. 新增 `ceo` 节点（node_type=1，permission_flag=role:<CEO 角色 id>）。
2. 原 `team_leader` 节点改名为 `ceo`，但保留 team_leader 角色 id 不变（只改显示名）。
3. 原 `dept_leader` 节点改名为 `supreme_decision_maker`（或保留 node_code 为 dept_leader，只改 node_name）。
4. 调整跳转：
   - `leader → ceo`
   - `ceo → gateway_amount`
   - `gateway_amount → end`（<1000）
   - `gateway_amount → supreme_decision_maker`（≥1000）
   - `supreme_decision_maker → end`

> 也可以把网关放在 CEO 之前：leader → 网关 → [≥1000 先 CEO → 最高决策人，<1000 CEO] → end。但用户明确说「提交→项目管理员→团队领导→部门领导」，所以先 CEO 再网关更贴合原意。

### 3.3 发票台账设计

#### 复用现有 `invoice_info` 表

新增字段（幂等 SQL 添加）：

| 字段名 | 类型 | 说明 |
|---|---|---|
| `acceptance_id` | bigint | 关联验收单 ID |
| `acceptance_item_id` | bigint | 关联验收明细 ID |
| `request_id` | bigint | 关联采购申请 ID |
| `project_id` | bigint | 关联项目 ID |
| `pdf_url` | varchar(1000) | 发票 PDF 文件 URL |
| `red_flag` | tinyint(1) | 是否冲红：0 否，1 是 |
| `valid_flag` | tinyint(1) | 是否有效：0 无效，1 有效 |
| `invalid_reason` | varchar(500) | 无效原因：重复、未匹配、多页、无法识别等 |
| `ocr_json` | text | OCR 识别的原始 JSON |

#### 发票来源

1. 验收时上传的发票 PDF，经 agents AI 识别后，把结果写入 `invoice_info`。
2. 每张发票根据「发票代码 + 发票号码」判断是否重复：
   - 若数据库中已存在相同发票代码+号码且 valid_flag=1，则新上传的发票标记为 `valid_flag=0, invalid_reason='发票重复'`。
3. 多上传的、未匹配到任何验收明细的发票：
   - `valid_flag=0`
   - `invalid_reason='未匹配到验收明细'`
4. 多页 PDF 只识别第一页，超页数的发票：
   - 仍可记录
   - `valid_flag=1`（如果匹配成功）
   - 在 OCR 结果或备注中提示「多页发票，仅识别第一页」

#### 发票页面

**推荐方案**：在现有「发票管理」模块下改造，新增「采购发票台账」页面。

页面功能：
- 列表展示所有发票（默认只显示 valid_flag=1）
- 筛选：有效发票 / 无效发票 / 全部
- 搜索：发票号码、销售方、关联验收单、关联项目
- 查看详情：展示 OCR 字段、关联订单/项目、PDF 预览
- 不单独提供「上传发票」入口（发票来自验收流程）
