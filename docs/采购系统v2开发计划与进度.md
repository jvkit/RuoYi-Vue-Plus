## 二、阶段划分（3 阶段，每阶段一个可体验闭环）

### Stage 1 · 数据地基 + 申请/审批闭环 ✅目标
- 幂等 SQL v2：改造 `pms_project`(+used_amount)、`pms_procurement_request`(+procurement_contact/payment_screenshot/quotation_url/invoice_info_json)；新增 `pms_attachment` 等 v2 全部表；菜单/字典/流程定义
- 后端改造：项目剩余资金、申请新字段+资金校验（超了**直接拒绝**）+leader/对接人自动带出、标题拼接、金额汇总
- 审批流：Warm-Flow「项目负责人 → 采购对接人」双节点（实时取 pms_project.leader）、单批/群批、节点到自己自动跳过、项目负责人自动获得所属项目审批权
- 通用附件表 + 附件服务（上传/下载/按 biz_type+biz_id 挂载）
- 前端：项目树、申请列表/表单/详情+流程图
- **交付点**：建项目 → 提申请(自购/对公) → 双人审批 全链路跑通

### Stage 2 · 验收 + 仓库 + 流转记录 闭环
- 验收：`pms_acceptance`+`pms_acceptance_item`、金额核对 pass/over、实物图+发票 PDF、验收完成自动入库
- 仓库：`pms_warehouse_stock`+`pms_stock_movement`+`pms_issue_request`、自动入库/手动添加/领用申请审批/流水不可删
- 流转记录：`pms_operation_log` 自动写日志 + 详情页时间线
- 前端：验收页、仓库库存、领用申请、流转时间线
- **交付点**：审批通过 → 验收 → 自动入库 → 领用出库 跑通

### Stage 3 · BOM 库三表 + 缺失单 + 合同 + 报销 闭环
- BOM：`pms_bom_catalog`+`pms_bom_table`+`pms_bom_node`（无限层级，替代旧 `pms_bom_item`）、组 N 套核对出缺失单、缺失单一键转采购申请
- 合同：`pms_purchase_contract`、模板渲染 + 导出
- 报销：`pms_reimbursement`、ZIP 打包（申请 Excel + 验收图 + 发票）
- 前端：BOM 库/表/节点树 + 核对页、合同、报销
- **交付点**：组 N 套 → 缺失单 → 转申请 → 合同 → 报销 全链路跑通

## 三、工程约定（务必遵守）

1. **版本**：开发在 6x；前端页面必须存在于 `plus-ui-6x/src/views`，后端菜单 `component` 字段与文件路径一一对应。
2. **SQL 幂等固化**：所有 DB 改动写入 `ruoyi-6x/script/sql/`，加 `SET NAMES utf8mb4;`，加列用 information_schema 判断、增删类先删后插、更新用 UPDATE，可重复执行。
3. **权限**：能力=权限点，用 RuoYi 原生角色+菜单/按钮权限+数据权限；验收复用采购同一套权限体系。
4. **附件**：统一 `pms_attachment` 表（biz_type + biz_id + file_url + file_name），验收/合同/报销都挂它。
5. **审批**：Warm-Flow，节点到自己自动跳过；单批（具体人）/群批（部门群体任一）。
6. **资金校验**：采购申请总金额 ≤ 项目剩余资金，**超了直接拒绝**（不是提示）。
7. **旧表**：`pms_bom_item`、`pms_supplier`、`pms_purchase_order(_item)` 保留不动，菜单隐藏。

### ⚠️ 待用户拍板的差异（前端自查发现）
1. **采购类型字典**：v2 文档 2.3 写 `goods物资/service服务/fixed_asset固定资产`，但实际字典（增量脚本 8-13 已改）与前端用的是 `material材料/equipment设备/service服务/engineering工程/dangerous危化品/other其他`。倾向保留后者（新字典），需确认是否同步改 v2 文档。
2. **申请状态机**：v2 文档 2.3 列 6 态 `draft/pending/approved/rejected/cancelled/finished`；RuoYi `BusinessStatusEnum` 是 7 态 `draft/waiting/finish/back/cancel/invalid/termination`。前端复用 RuoYi 枚举。"approved已通过"与"finished已完成"如何映射需确认：建议 审批通过=finish、验收完成由 `pms_acceptance.status` 单独跟踪（申请单不另加状态）。
3. **项目负责人 leader 字段类型**：当前 `pms_project.leader` 是 `varchar(100)` 存名字（实测数据是 "admin"/"321"/"231123" 等自由文本，非用户引用）。审批流"负责人→对接人"双节点要按负责人**分派任务给具体用户**，leader 必须能解析成用户 ID。建议：leader 改为存 `user_id`（前端项目表单改用户选择器），或新增 `leader_id` 列。
4. **对接人配置落点**：v2 说"admin 在部门/组织架构配置对接人"。需决定实现方式：扩 `sys_dept` 加字段 / 新建 `pms_procurement_contact` 配置表 / 复用角色。审批第二节点要按此解析成用户（单批=user_id，群批=dept_id）。
