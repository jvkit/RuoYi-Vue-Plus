# 采购系统业务扩展方案

> 目标：在现有 6x 采购系统（`ruoyi-6x/ruoyi-modules/ruoyi-procurement` + `plus-ui-6x`）基础上，落地「项目分级 / 采购 / 验收 / 出入库 / 报销 / BOM」六大板块。
> 本文档是对照业务需求的**落地规划**：区分「已有 / 改造 / 纯新增 / 外部依赖」，给出模块与表设计草案和实施路线。评审确认后再开发。

---

## 一、现状盘点（现有表结构）

| 表 | 关键字段 | 已覆盖能力 |
|---|---|---|
| `pms_project` | `parentId`(多级树)、`projectCode`、`projectName`、`leader`、`budget`、`startDate/endDate`、`status` | 项目多级树、编码自动生成 |
| `pms_supplier` | `supplierCode/Name`、`platform`(淘宝/京东/…)、`link`、`contact`、`bankName/Account` | 供应商档案 |
| `pms_bom_item` | `projectId`、`category`、品名/规格/品牌/数量/单位、`estPrice/estTotal`、`supplierId`、`status(0待采购/1已下单/2已到货)` | 单张物料清单 |
| `pms_procurement_request` | `requestCode`、`title`(自动拼接)、`titleType`(自购/对公)、`titleName`、`projectId`、`amount`、`purchaseType`、`status`、`processInstanceId` | 采购申请 + 标题拼接 + 工作流 |
| `pms_procurement_request_item` | `purchaseType`(科研/非科研)、`category1/2`、`projectBelong`、品名/规格/品牌/单位/数量/单价/金额、`bomItemId`、`link/platform/supplierId` | 明细分类树、明细级供应商、商品链接 |
| `pms_purchase_order(_item)` | 订单编号/标题、`requestId`、`projectId`、`supplierId`、金额、状态、明细 | 订单 |

**结论**：核心骨架（项目树 / 采购申请 / 明细分类 / 订单 / 单张 BOM / 供应商）已具备。缺口集中在「验收、仓库出入库、报销打包、合同生成、BOM 库表拆分、附件/图片、三人组、外部 AI/OA 对接」。

---

## 二、六大板块 → 现状映射

### 一、项目分级（长三角 / 天目湖 / 北京 → 项目 → 子项）
- **现状**：`pms_project.parentId` 已支持多级树，编码 `purp-日期-序号` 自动生成。
- **改造**：把**一级节点定义为「区域/项目群」**（长三角、天目湖、北京），二级=项目，三级+ =子项。区域就复用一个顶级项目节点，不必新建表。
  - 现有 `projectCode` 是"模块名+日期+三位序号"，一级区域/二级项目共用同一编号规则即可。
  - **待确认**：区域是否需要独立的「负责人/预算/是否启用」属性？若无，直接用顶级节点即可，最简单。

### 二、采购
| 需求 | 现状 | 处理 |
|---|---|---|
| 表格填写用户友好 | 已有 | 保留，继续打磨 |
| 导出中心 Excel 标准文件 | 无 | **新增**：按中心模板导出申请单（标题即文件名，加三位序数避免重名） |
| 链接扒型号/价格 | 无 | **外部依赖**：Agent 内置浏览器抓取（GPT 架构），先做接口预留，可后续接 |
| 每张采购表对应内部项目 | `request.projectId` ✓ | 已有 |
| 内外部申请人 / 三人组 | 无 | **改造**：`pms_procurement_request` 加字段：`procurement_contact`(采购对接人)、`internal_applicant`(内部申请人)、`leader`(项目负责人) |
| 自购 / 对公 | `titleType` ✓ | 已有 |
| 合同自动生成 | 无 | **新增**：合同模板 + 关键信息渲染（开票信息/规格/数量/单价）；合同/对公需报价单、淘宝类需付款截图 → 依赖附件能力 |
| 对接中心 OA | 无 | **外部依赖**：预留 webhook/接口，暂不做 |
| 物料录入仓库 | 无 | **新增**：仓库板块（见四） |
| BOM 库更新 | 单张 `pms_bom_item` | **改造**：拆 BOM库 vs BOM表（见六） |

### 三、验收
- **纯新增**模块。按采购申请逐条明细验收：实物拍照图 + 发票，AI 初审核对金额（发票金额 ≤ 申请价；超则提示冲红重开/重新提交）。验收人 = 三人组。
- **新增表** `pms_acceptance`（验收单）+ `pms_acceptance_item`（明细验收记录）+ 附件（图片/发票）。
- AI 金额核对可复用 Dify 服务经验（发票模块已有 `/invoice/info/extract`、`ai-review`）。

### 四、出入库
- **纯新增**：仓库板块展示所有已购物料；入库（验收后）；出库需领用申请 + 专人审批。
- **新增表**：`pms_warehouse`(仓库/库位)、`pms_stock`(库存)、`pms_stock_movement`(出入库流水)、`pms_issue_request`(领用申请+审批)。

### 五、报销
- **纯新增**：导出采购申请表 + 对应验收图 + 发票 → 打包压缩 → 邮件发送中心采购专员。
- 压缩/导出本地可做；**邮件发送 = 外部依赖**（SMTP 或中心 OA）。

### 六、BOM
- **改造 + 新增**：
  - **BOM 库**：筛选测试 OK 的物料（≠仓库，仓库是所有买过的物料）→ 录入库。
  - **BOM 表**：库内按产品线拆细的零件清单，一个产品线一张表，可增删查改，AI 完善字段。
- 现状 `pms_bom_item` 只有 `projectId`，无 product_line 维度 → 需引入「产品线」概念。

## 三、数据表草案（新增/改造）

> 遵循项目约定：新增/改动 SQL 一律固化为幂等脚本放 `ruoyi-6x/script/sql/`。

### 改造（加列，用 information_schema 判断幂等）
- `pms_procurement_request` +：`procurement_contact`(采购对接人)、`internal_applicant`(内部申请人)、`leader`(项目负责人)、`export_file_no`(导出文件序数，或由编码/时间戳保证不重名)
- `pms_project` +：如需区域独立属性则加 `is_group`、`region` 等（否则不加）

### 新增
```
pms_acceptance           验收单：id, request_id, accept_no, leader(验收人), status, accept_date, remark
pms_acceptance_item      验收明细：id, acceptance_id, request_item_id, item_name, apply_price, invoice_price,
                          ai_opinion, ai_passed, photo_url(实物图), invoice_url(发票图), result(通过/冲红), remark
pms_warehouse            仓库/库位：id, name, location, keeper(看管人), status
pms_stock                库存：id, warehouse_id, bom_item_id(或物料标识), item_name, spec, unit, qty, ...
pms_stock_movement       库存流水：id, stock_id, type(in/out), qty, relate_id(来源单), create_by, time
pms_issue_request        领用申请：id, stock_id, qty, applicant, approver, status(待审/通过/拒绝), time
pms_purchase_contract    采购合同：id, request_id, contract_no, template_id, key_json(开票/规格/数量/单价),
                          attach_url(报价单/付款截图), status, content(渲染结果)
pms_product_line         BOM产品线：id, project_id, line_name, remark      -- BOM表维度
pms_bom_table            BOM表：id, line_id, bom_item_id, qty, ...          -- 库内产品线的零件组成
pms_attachment           通用附件（可选）：id, biz_type, biz_id, file_url, file_name   -- 图片/发票/报价单统一挂载
```

> 附件两种做法：① 统一 `pms_attachment` 表（推荐，验收/合同/报销都能复用）；② 每表直接存 URL 字段。建议走①，减少重复。

## 四、实施路线（按优先级）

> 建议按「先闭环主流程，再补 AI/外部」推进，每步都可在 6x 上独立验证。

1. **采购申请补三人组 + 中心 Excel 导出**（改造，工作量小，立即闭环采购）
   - 加三字段、导出模板 + 文件名序数去重。
2. **通用附件能力**（`pms_attachment`，为验收/合同/报销打地基）
3. **验收模块**（表 + 页面 + AI 金额核对，复用 Dify）
4. **仓库 + 出入库**（入库挂验收、领用申请 + 看管人审批）
5. **BOM 库/表拆分 + 产品线**（改造现有 `pms_bom_item`）
6. **报销打包 + 邮件**（导出/压缩本地先做，邮件留接口）
7. **合同自动生成**（模板渲染，报价单/付款截图挂附件）
8. **外部依赖预留**：中心 OA 对接、链接扒价（Agent 浏览器）、发票真伪等 —— 接口先留，不阻塞主线

## 五、待确认的关键决策

1. **项目分级**：区域（长三角/天目湖/北京）是否复用顶级 `pms_project` 节点即可？还是需要独立的区域表/独立属性（负责人、启用）？
2. **三人组字段**：`采购对接人 / 内部申请人 / 项目负责人` 放申请单；项目负责人是否直接沿用 `pms_project.leader`，还是申请单里单独填？
3. **附件方案**：统一 `pms_attachment` 表（推荐）还是各模块内嵌 URL 字段？
4. **BOM 产品线**：BOM 表（产品线零件清单）挂在「项目」还是「区域」下？一张产品线表对应一个仪器/产品。
5. **报销/合同/链接扒价**：这三块依赖外部（SMTP 邮件、中心模板、Agent 浏览器），是否先只做本地部分 + 接口预留，外部能力后续再接？
6. **实施范围**：先按上面 1-2 步（采购闭环）动手，还是一口气铺全？建议先做 1-2，验证风格后再铺。

---

## 六、风险与说明
- 采购分类树、编码规则、标题拼接、发票迁移等此前已完成并验证，方案在其上扩展。
- 所有 DB 改动走幂等脚本，换环境/上生产可复现。
- 外部依赖（中心 OA、邮件、Agent 扒价）不阻塞主线，接口预留。
