## 一、为什么需要工作流引擎

你可能想过：审批不就是"填个单，存个状态，谁点一下就改状态"吗？为什么要一套复杂的引擎？

**自己写（不用引擎）的问题：**

- 状态散落在每张业务表里，每个模块都要自己写 if/else 改状态
- 流程要改（比如加一级审批、换个审批人）就得改代码、重新发布
- 退回、流转记录、超时提醒这些通用能力，每个模块都要重新造
- 业务表里只有"最终结果"，说不清"这单走到哪了、谁批过、谁退过"

**工作流引擎做的事：**

把"流程怎么走"从业务代码里抽出来，变成一张**可配置的图纸**。业务只管说"我这单到哪一步了"，引擎负责：

- 这一步该谁来办
- 办完之后下一步是谁
- 整个流程现在是什么状态
- 完整留痕（谁在哪一步做了什么）

Warm-Flow 就是这样一个引擎。RuoYi-Vue-Plus 把引擎内嵌成了 `ruoyi-workflow` 模块，采购审批、请假审批都跑在它上面。

## 二、三个核心概念：定义 / 实例 / 任务

这是整个工作流最重要的三个词，先记住它们：

| 概念 | 类比 | 说明 |
|---|---|---|
| **流程定义**（Definition） | 图纸 / 剧本 | 流程长什么样：有哪些节点、节点之间怎么连 |
| **流程实例**（Instance） | 一次开工 / 一场演出 | 某一次具体的流转。同一张图纸可以开工无数次 |
| **任务**（Task） | 一个待办 / 一个环节 | 流程走到某个节点时，生成一条"该谁办理"的待办 |

它们的关系：

```
一张图纸(定义) ──开工──▶ 无数个实例(每一次提交) ──走流程──▶ 若干任务(待办)
```

打个比方：

- **定义** = 一张"员工请假审批流程图"（贴在墙上那张）
- **实例** = 张三今天请假的这一次流程，李四明天请假的另一次流程
- **任务** = 此刻这张请假单正停在"组长审批"这一步，组长有一个待办

关键点：**实例和定义是多对一，实例和任务是 一对多**。一个实例在某一时刻可能同时有几个待办（比如会签、并行审批时），但绝大多数简单流程同一时刻只有一个待办。

## 三、流程长什么样：节点 + 连线

流程定义由两部分组成：**节点** 和 **连线**。

### 3.1 节点（Node）

一个节点就是流程中的一个"环节"。类型有三种：

| 类型 | 含义 | 例子 |
|---|---|---|
| **开始节点** | 流程从这启动 | "开始" |
| **中间节点**（审批节点） | 需要人办理的环节 | "申请人""组长""负责人""对接人" |
| **结束节点** | 流程走完 | "结束" |

每个审批节点还要回答一个问题：**这一步谁有权办理？** 常见的几种写法：

| 写法 | 含义 |
|---|---|
| 发起人自己 | 这个环节由提交申请的人办理（通常是"申请人确认提交"这一步） |
| 某个人 | 指定具体某个人来批 |
| 某个角色 | 这个角色下的任意一人来批即可 |
| 某个变量 | 流程启动时动态指定（比如"负责人是谁"由申请单上选的负责人决定） |

### 3.2 连线（Skip）

节点之间用"线"连起来，线上标明**什么情况下往哪走**。最常见的两种：

| 线类型 | 含义 |
|---|---|
| **PASS（通过）** | 办理人点了"通过"，流程沿着这条线走 |
| **REJECT（拒绝）** | 办理人点了"拒绝/退回"，流程沿着这条线走 |

### 3.3 一张真实的图

下面这张是采购审批的流程（简化示意）：

```
                    ┌───────────────┐
                    │   开始节点     │
                    └──────┬────────┘
                           │  PASS（提交）
                           ▼
                    ┌───────────────┐
                    │ 负责人审批节点 │◀──┐
                    └───┬───────┬───┘   │
                        │PASS   │REJECT │
                        ▼       │       │
                 ┌─────────────┐│       │
                 │对接人审批节点││       │
                 └──┬──────┬──┘│       │
                    │PASS   │REJECT     │
                    ▼       │           │
             ┌──────────┐   └──▶ 退回 ──┘
             │ 结束节点 │
             └──────────┘
```

也就是：

- 开始 →（提交）→ 负责人审批
- 负责人通过 → 对接人审批；负责人拒绝 → 退回开始
- 对接人通过 → 结束；对接人拒绝 → 退回开始

这就是你之前说的"负责人 + 对接人两级审批"。引擎不管业务含义，它只认这张图上"谁连谁、什么情况下走哪条线"。

## 四、审批是怎么"走"起来的（skip 机制）

这是引擎最核心的机制，理解了它，整个工作流就通了。

**引擎没有一堆 if/else 的业务逻辑，它只有一条铁律：**

> **办完当前节点的任务 → 看办理人点了"通过"还是"拒绝" → 沿着对应那条线 → 走到下一个节点 → 生成下一个节点的待办 → 更新流程状态**

这个"沿着线走一步"的动作，就叫 **skip（跳转/流转）**。

每次 skip 做了四件事：

1. **当前任务标记为"已办完"** → 挪进历史记录（留痕）
2. **找线**：看当前节点连出去的线里，哪条是 PASS、哪条是 REJECT，按办理人点的走
3. **生成新任务**：到下一个节点，给该节点的办理人生成一条新待办
4. **更新状态**：根据走到哪了、怎么走的，更新流程的整体状态

所以记住一句话：

> **流程的每一步，都是"办完当前任务 → skip 一下 → 生成下一个任务"。**

流程不是一次性"创建出来"的，而是一步一步 skip 出来的。每个审批节点都是一条"任务"等着被办。

## 五、一套流程能走多遍（实例）

图纸（定义）只有一份，但每天会有很多次审批，每次审批就是**一个实例**。

- 张三提交采购申请 → 实例 A
- 李四提交采购申请 → 实例 B
- 王五提交采购申请 → 实例 C

实例 A、B、C 用的是同一张图纸，但彼此完全独立：各自走到哪一步、各自什么状态、各自谁在办，互不影响。

实例还会记住"我这单对应哪个业务单据"——因为流程本身只管"怎么走"，它不知道也不关心"这是一张采购单还是请假单"。是业务方在启动流程时告诉引擎"我这个实例对应哪张业务单"。

所以：

- **引擎层**（流程定义、实例、任务）跟业务是解耦的，通用
- **业务层**（采购单、请假单）提供"我这单"和"我的审批人"，并消费"流程走到了哪一步"

## 六、状态到底有几种（重点，最容易混）

你之前纠结的"draft / waiting / finish"到底是谁的状态？这里彻底讲清楚。

**注意：系统里有两套状态，各管各的，千万不要混。**

### 第一套：业务状态（给人看的）

| 状态 | 含义 |
|---|---|
| draft（草稿） | 单子还没提交，能编辑 |
| waiting（待审核） | 已提交，正在等审批 |
| finish（已完成） | 审批走完了 |
| back（已退回） | 被退回，需修改重新提交 |
| cancel / invalid / termination | 撤销 / 作废 / 终止 |

**这套状态存在业务表里**（比如采购申请那张表），是列表页、详情页展示给用户看的。它的作用是：告诉业务"这单处于什么阶段、该显示什么按钮"。

### 第二套：引擎内部状态（引擎算的）

引擎内部还有一套自己的状态，比如：

| 状态 | 含义 |
|---|---|
| 待提交（TOBESUBMIT） | 流程刚建，还没正式提交 |
| 审批中（APPROVAL） | 有任务在等着办 |
| 已完成（FINISHED） | 走完了 |
| 已拒绝（REJECT） | 被拒了 |

**这套状态是引擎在 skip 的时候自动算出来的**，存在流程任务/实例上。它跟"业务状态"不是同一个东西，但会对应起来。

### 两套状态怎么同步？

引擎每走一步，会通过一个"监听器"（可以理解成"引擎走一步就会通知一声"）把最新情况告诉业务方，业务方再据此更新自己的业务状态。

```
引擎 skip 一步
   ↓
触发监听器（引擎的"广播"）
   ↓
业务方收到通知，把业务状态改掉
   ↓
列表页/详情页显示的就是这个业务状态
```

所以业务状态是**引擎走了之后，业务被"通知"着去改的**，不是业务自己拍脑袋设的。这样两边永远一致，也不会出现"业务说已通过、引擎其实还没走完"的错乱。

## 七、完整走一遍：从提交到结束

把上面的概念串起来，看一次完整的采购审批：

| 步骤 | 谁做的 | 引擎里发生了什么 | 业务状态 |
|---|---|---|---|
| 1 | 用户填单 | 生成一张"草稿"单 | draft（草稿） |
| 2 | 用户点"保存草稿" | 什么都不启动，只是存起来 | draft（草稿） |
| 3 | 用户点"提交申请" | **启动流程**：建实例 + 建第一个待办（申请人自己确认提交） | draft（草稿） |
| 4 | 申请人确认提交 | 办理第一个待办，skip 一下 | **draft → waiting（待审核）** |
| 5 | 负责人收到待办，点"通过" | 负责人任务完成，skip 到对接人节点 | waiting（待审核） |
| 6 | 对接人收到待办，点"通过" | 对接人任务完成，skip 到结束节点 | **waiting → finish（已完成）** |

注意第 3 和第 4 是两回事：

- **第 3 步"启动流程"** 只是把流程"建"起来，此时还是草稿
- **第 4 步"确认提交"** 才是真正把流程推进到"待审核"，给负责人生成待办

**这就是之前那个 bug 的根源**：采购申请提交时只做了第 3 步（启动流程），漏掉了第 4 步（办理第一个待办），所以流程永远停在草稿，负责人的待办一直没生成，看起来就是"审批卡住了、待办里没有"。

## 八、用生活例子再讲一遍

把工作流想成**一个接力赛**：

- **图纸（定义）** = 比赛规则：第一棒谁跑、第二棒谁跑、跑完给谁
- **每次比赛（实例）** = 今天这场、明天那场，各自独立
- **接力棒（任务）** = 当前这棒该谁拿
- **交接动作（skip）** = 前一棒跑完，把棒交给下一棒
- **赛程表（状态）** = 现在比到第几棒、处于什么阶段

采购审批就是一个三棒接力：

```
第一棒：申请人（确认提交）
   ↓ 交接（通过）
第二棒：负责人（审批）
   ↓ 交接（通过）
第三棒：对接人（审批）
   ↓ 交接（通过）
冲线（结束）
```

如果第二棒（负责人）迟迟不跑，那整场比赛就卡在第二棒——这正好对应你遇到的"审批卡住"。

## 九、常见问题速查

### Q1：为什么"待办"里看不到我的单？

待办列表只显示**已提交（waiting）**的单。如果流程还在草稿阶段（没完成"确认提交"那一步），就不会出现在任何人的待办里。

### Q2：为什么我的单显示"草稿"？

两种可能：
1. 你只是保存了草稿，没提交
2. 提交逻辑有 bug，流程建了但没推进（就是我们之前那个问题）

### Q3：把状态改成"waiting"不就能看到了吗？

能"看到"，但这是**骗过了列表查询**，引擎内部其实还停在草稿。等你点"通过"时，引擎按自己的规则重新算状态，发现对不上，就会出错。**正确做法是让流程真正走完那一步，而不是手改状态。**

### Q4：为什么审批要分"启动流程"和"确认提交"两步？

因为引擎把"提交"也设计成了流程的一个环节（申请人节点）。这样引擎就能统一处理"每一步谁办、办了往哪走"，不用为"提交"单独写一套逻辑。多出来的一步，是为了引擎规则统一。

### Q5：退回之后还能重新提交吗？

能。退回 = 走 REJECT 线回到前面的节点（通常是回到申请人），业务状态变"已退回（back）"。申请人改完再提交，等于重新走一遍。
