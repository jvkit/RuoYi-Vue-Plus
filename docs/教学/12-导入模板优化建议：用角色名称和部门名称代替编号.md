# 12-导入模板优化建议：用角色名称和部门名称代替编号

## 1. 为什么现在的模板用编号？

RuoYi 自带的导入功能是为了**最小改动、最快实现**：

- `SysUserImportVo` 里的字段直接对应 `sys_user` 表的字段。
- `dept_id`、`role_id` 都是数据库里的外键。
- 导入监听器直接把 Excel 的值塞进 BO，然后调用 Service 写入数据库。

所以模板里写的是 `dept_id`、`role_id` 这些编号，而不是名称。

## 2. 用编号的问题

对实际使用者（比如 HR）来说，编号毫无意义：

| 列 | 当前要求 | 使用者视角 |
|---|---|---|
| 部门编号 | `2080532456532725762` | 这是啥？我去哪查？ |
| 角色编号 | `2080534408574390273` | 这又是啥？ |

前端页面上显示的是「部门名称」「角色名称」，根本不显示编号。

所以用名称代替编号，体验会好很多。

## 3. 优化后的模板长什么样？

| 用户账号 | 用户昵称 | 部门名称 | 角色名称 | 用户性别 | 账号状态 |
|---|---|---|---|---|---|
| zhangsan | 张三 | 长三角物理研究中心 | 普通用户 | 男 | 正常 |
| lisi | 李四 | 研发部 | 普通用户 | 女 | 正常 |
| manager1 | 王经理 | 研发部 | 部门经理 | 男 | 正常 |

这样 HR 直接看名称填表，不用查数据库。

## 4. 后端需要做哪些改动？

### 4.1 改导入 VO

```java
public class SysUserImportVo {
    // 原来
    // private Long deptId;

    // 改成
    @ExcelProperty(value = "部门名称")
    private String deptName;

    // 原来
    // private Long[] roleIds;

    // 改成
    @ExcelProperty(value = "角色名称")
    private String roleName;
}
```

### 4.2 改导入监听器

在 `SysUserImportListener.invoke()` 里，根据名称查 ID：

```java
// 根据部门名称查部门 ID
SysDept dept = deptMapper.selectOne(new LambdaQueryWrapper<SysDept>()
    .eq(SysDept::getDeptName, userVo.getDeptName())
    .eq(SysDept::getTenantId, LoginHelper.getTenantId()));
if (dept != null) {
    user.setDeptId(dept.getDeptId());
}

// 根据角色名称查角色 ID
SysRole role = roleMapper.selectOne(new LambdaQueryWrapper<SysRole>()
    .eq(SysRole::getRoleName, userVo.getRoleName())
    .eq(SysRole::getTenantId, LoginHelper.getTenantId()));
if (role != null) {
    user.setRoleIds(new Long[]{ role.getRoleId() });
}
```

> 注意：要根据当前租户过滤，不能跨租户查到别人的角色/部门。

### 4.3 处理找不到的情况

如果 Excel 里填的部门名称或角色名称不存在，应该导入失败并给出明确提示：

```text
账号 zhangsan 导入失败：部门「研发部」不存在
账号 lisi 导入失败：角色「普通用户」不存在
```

## 5. 用名称代替编号的风险

### 5.1 名称可能重复

- **角色名称**：一个租户内一般不允许重复，可以按名称唯一查找。
- **部门名称**：不同父部门下可能有同名子部门（比如两个「财务部」），按名称查会冲突。

解决：

- 部门名称加父部门前缀，例如「总公司/财务部」。
- 或者同时提供「部门编号」和「部门名称」两列，名称用于展示，编号用于精确匹配。

### 5.2 多租户隔离

同一个系统里，A 公司和 B 公司可能都有「普通用户」这个角色。查找时一定要加上 `tenant_id` 条件，否则可能把 A 公司用户配到 B 公司角色上。

## 6. 推荐做法

如果你后续要优化导入功能，建议这样设计模板：

| 用户账号 | 用户昵称 | 部门名称 | 角色名称 | 用户性别 | 账号状态 |
|---|---|---|---|---|---|

后端逻辑：

1. 根据 `角色名称` + 当前租户 ID 查找 `role_id`。
2. 根据 `部门名称` + 当前租户 ID 查找 `dept_id`。
3. 如果找不到，明确报错。
4. 找到后，正常写入用户并分配角色。

## 7. 如果部门名称可能重复

可以在模板里同时保留两列：

| 部门编号 | 部门名称 | 角色名称 |
|---|---|---|
| | 研发部 | 普通用户 |

后端规则：

- 如果填了部门编号，直接用编号。
- 如果没填编号但填了部门名称，按名称查。
- 名称查出来多个，报错提示用户补充编号。

这样既有友好性，又有精确性。

## 8. 总结

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| 用编号 | 实现简单、精确 | 对使用者不友好 | 技术后台、少量用户 |
| 用名称 | 对 HR 友好 | 可能重名、需要查库转换 | HR 批量入职 |
| 编号+名称 | 既友好又精确 | 模板稍复杂 | 正式系统 |

对于你们现在的场景，后续优化导入时，**直接用「角色名称」和「部门名称」是合理的**，只需在导入监听器里多做一步名称转 ID 的查询。
