# 06-权限、角色、用户与多租户概念

## 1. 权限管理是不是在 Controller 层实现的？

**是的，但不止 Controller。**

RuoYi-Vue-Plus 的权限控制分三层：

| 控制层级 | 代码位置 | 控制什么 |
|---|---|---|
| **菜单可见性** | 后端 `sys_menu` 表 | 用户登录后左侧菜单显示哪些 |
| **接口访问权** | 后端 Controller 的 `@SaCheckPermission` | 用户能不能调用某个 HTTP 接口 |
| **按钮显示权** | 前端 `v-hasPermi` | 用户页面上能不能看到某个按钮 |

三者靠同一个东西串联：**权限字符**（也叫权限标识）。

---

## 2. 权限字符是什么？

权限字符就是一个字符串，格式通常是三段式：

```
模块:功能:动作
```

例如发票模块：

```
invoice:info:list      查看发票列表
invoice:info:add       新增发票
invoice:info:edit      修改发票
invoice:info:remove    删除发票
invoice:info:export    导出发票
invoice:info:query     查询发票详情
```

### 2.1 权限字符三处必须一致

同一个权限字符要出现在三个地方：

1. **数据库菜单表** `sys_menu.perms`
2. **后端 Controller** 的 `@SaCheckPermission("invoice:info:add")`
3. **前端页面** 的 `v-hasPermi="['invoice:info:add']"`

只要有一处对不上，权限就会出问题。

### 2.2 举个例子

数据库里有这条记录：

```sql
INSERT INTO sys_menu (menu_name, menu_type, perms, ...)
VALUES ('发票信息新增', 'F', 'invoice:info:add', ...);
```

后端接口：

```java
@SaCheckPermission("invoice:info:add")
@PostMapping()
public R<InvoiceInfoVo> add(...) { ... }
```

前端按钮：

```vue
<el-button v-hasPermi="['invoice:info:add']" @click="handleAdd">新增</el-button>
```

这样：

- 没这个权限的用户，左侧菜单看不到「发票信息」。
- 没这个权限的用户，直接调用 POST /invoice/info 会被拒绝。
- 没这个权限的用户，页面上看不到「新增」按钮。

---

## 3. 能不能设计一个「发票管理员」角色，其他人只能上传？

**完全可以。**

RuoYi 的权限模型是：

```
用户 → 角色 → 权限
```

一个用户可以有一个或多个角色，一个角色可以拥有多个权限。

### 3.1 设计两个角色

你可以这样设计：

| 角色 | 权限 |
|---|---|
| **发票管理员** | `invoice:info:list/add/edit/remove/export/query` |
| **普通员工** | `invoice:info:list/add` |

普通员工能查看列表、能新增发票，但不能修改、删除、导出。

### 3.2 如果想让员工只能「上传」不能「看全部」

这属于更细的业务权限，通常有两种做法：

#### 做法 1：数据权限

RuoYi 自带数据权限机制：

- 全部数据
- 本部门数据
- 本部门及以下数据
- 仅本人数据
- 自定义权限

如果普通员工只能看自己上传的发票，管理员能看全部，可以在 Service 层加数据权限过滤。

#### 做法 2：自己写业务规则

比如在 Service 里判断：

```java
if (!当前用户是管理员 && !数据创建人.equals(当前用户)) {
    throw new ServiceException("无权查看他人发票");
}
```

这种更灵活，但需要自己写代码。

## 4. 普通员工怎么注册账号？

RuoYi-Vue-Plus 默认**不是开放注册的**，而是管理员在后台创建账号。

### 4.1 管理员创建用户

登录 `admin` 账号，进入：

```
系统管理 → 用户管理 → 新增
```

填写用户名、密码、归属部门、岗位，然后分配角色。

这是企业 OA 最常见的做法：HR 或管理员统一开户。

### 4.2 能不能开放自助注册？

可以，但通常不推荐用于企业内部 OA。

开启方式：

```
系统管理 → 参数管理 → 找到注册开关
```

或者修改配置 `sys_config` 表里控制注册的参数。

开启后，登录页面会出现「注册」入口。但注册出来的用户默认没有角色、没有菜单权限，几乎什么都看不到，还需要管理员手动授权。

## 5. 目前系统有哪些功能是给普通员工用的？

RuoYi-Vue-Plus 本质上是一个**管理后台框架**，不是开箱即用的完整 OA。但它已经包含了一些员工可以用的模块：

### 5.1 工作流模块（员工最常用）

路径：左侧菜单 **工作流**

员工可以：

- **请假申请**：填写请假单，提交审批。
- **我的待办**：查看需要自己审批的流程。
- **我发起的**：查看自己提交的流程进度。
- **我的已办**：查看自己处理过的流程。

这些是典型员工操作：提交申请、查看进度、处理审批。

### 5.2 采购申请模块

路径：**采购管理 → 采购申请**

员工可以提交采购申请，走审批流程。

### 5.3 发票管理模块（本次新增）

路径：**发票管理 → 发票信息**

员工可以上传发票信息，管理员可以管理全部发票。

### 5.4 系统监控/工具（管理员用）

以下模块通常是管理员或开发人员用，普通员工不需要：

- 系统管理（用户、角色、菜单、部门、岗位、字典、参数）
- 系统监控（在线用户、定时任务、数据监控、服务监控）
- 系统工具（代码生成、系统接口）

### 5.5 目前缺少的员工功能

如果要做成完整的企业 OA，以下功能目前**没有内置**，需要二次开发：

- 考勤打卡（上下班打卡、考勤统计）
- 加班申请
- 报销申请
- 出差申请
- 会议室预定
- 公告通知（系统公告有，但比较简单）
- 通讯录/组织架构树
- 文件管理
- OKR / 绩效管理

RuoYi 给你的不是一套完整 OA，而是一个**带用户、权限、菜单、工作流、代码生成器的基础平台**。业务模块需要自己按需开发。

## 6. 多租户是什么意思？

**多租户 = 一套系统可以同时给多个公司（租户）用，彼此数据隔离。**

### 6.1 举个具体例子

假设你部署了一套 RuoYi-Vue-Plus：

- 公司 A 用：`https://a.oa.com`
- 公司 B 用：`https://b.oa.com`

两家公司在同一套代码、同一个数据库里运行，但：

- A 公司的员工看不到 B 公司的数据。
- A 公司的菜单、角色、流程可以独立配置。
- A 公司的管理员只能管 A 公司的人。

### 6.2 怎么实现的？

核心就是每张业务表都有一个 `tenant_id` 字段：

```sql
CREATE TABLE invoice_info (
  id bigint,
  tenant_id varchar(20) DEFAULT '000000',
  invoice_number varchar(50),
  ...
);
```

用户登录时，系统会知道当前用户属于哪个租户。查询数据时，框架会自动加上：

```sql
WHERE tenant_id = '当前租户ID'
```

这样 A 公司和 B 公司的发票数据自然隔离。

### 6.3 多租户和「为多个公司定制 OA」是不是一回事？

**基本是的，但不完全等同。**

多租户系统可以为多个公司提供 OA 服务，但「定制」程度取决于你怎么开发：

- **基础多租户**：所有公司用同一套功能，只是数据隔离。类似 SaaS 标准化产品。
- **深度定制**：每个租户可以有自己的菜单、角色、流程、字段、甚至独立模块。RuoYi 的菜单和权限是按租户可配的，所以可以做到一定程度的定制。

### 6.4 我们现在的环境是多租户吗？

是的，RuoYi-Vue-Plus 默认开启了多租户。

你登录的 `admin` 账号属于默认租户 `000000`。如果以后要给其他公司用，可以在：

```
系统管理 → 租户管理
```

里新增租户。

## 7. 总结

| 问题 | 答案 |
|---|---|
| 权限在 Controller 实现吗？ | Controller 做接口权限，数据库做菜单权限，前端做按钮权限 |
| 能不能做「发票管理员 vs 普通员工」？ | 能，通过角色分配不同权限 |
| 普通员工怎么注册？ | 通常管理员后台创建；也可以开自助注册，但注册后需授权 |
| 目前员工能用啥？ | 工作流（请假/审批）、采购申请、发票上传 |
| 还缺哪些 OA 功能？ | 考勤、加班、报销、出差、会议室、文件管理等 |
| 权限字符是什么？ | `模块:功能:动作`，三处（菜单、Controller、前端）要对齐 |
| 多租户是什么意思？ | 一套系统服务多个公司，数据按 `tenant_id` 隔离 |
| 这是万能 OA 壳子吗？ | 是带权限和流程的「壳子」，具体业务模块需要自己开发 |

---

## 8. 下一步建议

如果你准备做一个完整的企业 OA，建议按这个顺序扩展：

1. **用户和角色**：先给不同岗位设计角色（普通员工、部门经理、财务、管理员）。
2. **工作流**：把请假、报销、采购、发票认证等流程用 Warm-Flow 串起来。
3. **考勤模块**：开发打卡、请假、加班、出差。
4. **报表/统计**：给管理员看各部门的申请、报销、考勤统计。

目前可以先不急着写代码，先把每个业务模块的权限、流程、表结构想明白。
