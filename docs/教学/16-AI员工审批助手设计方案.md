# 16-AI 员工审批助手设计方案

> 目标：把「AI 员工作为审批资源」做成一套通用、可落地的方案

---

## 一、核心思路

1. **把 AI 定位为「资源」而非「部门里的人」**
   - 它不属于某个具体员工，不占用人事编制，也不受离职/调岗影响。
   - 在 RuoYi 里，可以把它当成一个特殊的「系统用户」或「代理人节点」。

2. **责任边界交给申请人**
   - 申请人上传证据，AI 只负责「形式审查」：材料是否齐全、是否符合公司明文规则。
   - 造假责任由申请人承担，也就是「形式审查 + 事后追责」。

3. **不是秒批，而是「预审批 + 人类一键确认」**
   - 负责人上线后看到 AI 的分类结果：直接通过 / 拒绝 / 需补材料 / 需人工裁定。
   - 这符合合规要求：AI 提建议，人类做最终决策。

---

## 二、一些可能的问题

### 1. 证据真实性只是「形式审查」

AI 目前无法判断一张病假条是不是 PS 的、一张聊天截图是不是伪造的，但是ai或比真人还准确，但是无法要求ai必定不出错；
所以只能做：

- 有没有这个文件？
- 文件类型对不对？（图片/PDF）
- 图片里有没有出现关键字？（如「医院」「诊断证明」「日期」）
- 日期是否在请假范围内？

真正的防伪要靠：

- 对接医院/学校/供应商的官方接口验真（成本高）。
- 或者明确写入公司制度：「上传虚假材料按旷工/违纪处理」。

### 2. 谁对 AI 的决策负责？

在法律和审计层面，AI 不能承担责任。因此系统必须：

- 记录 AI 每一步判断依据（日志可审计）。
- 关键节点必须由真人点击「确认通过/拒绝」。
- 保留人类推翻 AI 建议的能力。

### 3. 不同类型的审批规则差异很大

| 审批类型 | 需要的证据 | AI 能判断什么 | AI 不能判断什么 |
|---|---|---|---|
| 病假 | 医院诊断证明 | 有没有证明、日期是否覆盖请假时间 | 证明是否伪造 |
| 事假 | 事由说明 | 有没有填写事由、字数是否合规 | 事由是否真实 |
| 采购申请 | 采购原因、预算、供应商信息 | 必填项是否齐全、金额是否超预算 | 采购是否必要 |
| 付款申请 | 合同、发票、验收单 | 三单是否齐全、金额是否一致 | 合同是否真实 |
| 报销 | 发票、行程单、消费明细 | 发票金额与报销金额是否一致 | 发票是否虚开 |

所以必须让业务管理员能**自己配置审批规则**，而不是每个类型都写死代码。

### 4. 多租户下的隔离

RuoYi-Vue-Plus 是多租户系统。A 公司的 AI 规则不能用到 B 公司：

- 病假规则可能不同（有的公司要求二甲医院，有的要求三甲）。
- 采购审批阈值不同。
- 通知对象不同。

所以 AI 规则表必须带 `tenant_id`。

### 5. 通知能力不等于能打扰任何人

AI 向员工发通知没问题，但要防止滥用：

- 通知应该有模板和频次限制。
- 被询问人（如「你确实让张三采购这批设备吗？」）必须有明确身份，否则会被当成骚扰。
- 最好支持多种通道：站内信、企业微信/钉钉/飞书、邮件。

### 6. AI 也会错

可能出现：

- 漏看关键信息（图片模糊、手写体）。
- 理解错规则（把「3 天以内」理解成「3 天及以上」）。
- 幻觉（编造不存在的证据）。

所以要有：

- 置信度分数：低于阈值就自动转人工。
- 申诉/纠错机制：申请人可以说「AI 看错了，请人工复核」。

## 三、基于 RuoYi 的落地方案

### 3.1 整体架构

```
申请人提交审批
    ↓
[工作流引擎 Warm-Flow] 走到 AI 审批节点
    ↓
AI 审批服务（新模块 ruoyi-ai-agent）
    ↓
调用大模型 API（自研 / Kimi / 文心 / 通义等）
    ↓
返回审批结论：通过 / 拒绝 / 补材料 / 转人工
    ↓
工作流继续流转 或 挂起等待人类确认
    ↓
通知相关人（站内信 / IM / 邮件）
    ↓
负责人在 UI 上一键处理 AI 建议
```

### 3.2 对 RuoYi 的改动点

| 层级 | 改动内容 |
|---|---|
| 数据库 | 新增 `ai_approval_rule`、`ai_approval_log`、`ai_approval_task` 等表 |
| 后端模块 | 新建 `ruoyi-ai-agent` 模块，提供规则配置、AI 调用、结论回调 |
| 工作流 | 在 Warm-Flow 中新增一种节点类型：AI 审批节点 |
| 前端 | 新增「AI 审批规则配置」页面；在审批详情页显示 AI 建议 |
| 通知 | 复用 RuoYi 消息通知模块，扩展 AI 发起通知的能力 |

### 3.3 规则配置设计（关键）

每个审批类型配一套规则，业务管理员可以在前端配置：

```yaml
审批类型: 病假
所需证据:
  - 字段: 医院诊断证明
    类型: 图片或PDF
    必填: 是
    AI检查点:
      - 是否包含"诊断"或"病假"关键字
      - 日期是否覆盖请假起止日期
通过条件:
  - 所有必填证据齐全
  - 所有检查点通过
拒绝条件:
  - 证据类型错误（如上传了 Word）
  - 日期明显不匹配
转人工条件:
  - AI 置信度 < 0.8
  - 申请人发起申诉
通知对象:
  - 直属上级
  - HRBP
```

### 3.4 AI 调用方式二选一

#### 方案 A：自研 Agent（推荐长期用）

- 自己封装大模型 API。
- 自己写 Prompt、解析返回结果。
- 优点：完全可控、可按公司规则微调、成本可控。
- 缺点：开发周期长、需要 Prompt 工程能力。

#### 方案 B：接入现有智能体

- 通过 API 或 MCP/Function Call 让外部 Agent 帮你判断。
- 优点：启动快、不需要自己训练模型。
- 缺点：
  - 需要把企业内部数据传给第三方，存在隐私风险。
  - 可控性差，结论格式可能不稳定。
  - 按调用量付费，成本高。

**建议**：先用方案 B 做原型验证（PoC），验证价值后再迁移到方案 A。

## 四、通用能力抽象：不止于审批

把 AI 员工做成一个通用能力平台，未来可以扩展：

| 场景 | AI 能力 | 人类角色 |
|---|---|---|
| 审批助手 | 预审批、分类、补材料提醒 | 最终确认 |
| 智能客服 | 回答员工常见问题（考勤、报销规则） | 处理无法回答的问题 |
| 会议纪要 | 自动整理会议录音/文字 | 确认和补充 |
| 合同初审 | 检查合同关键条款是否缺失 | 法务最终审核 |
| 发票稽核 | 检查发票与报销单是否匹配 | 财务最终审核 |
| 招聘初筛 | 根据 JD 筛选简历 | HR 最终面试 |

核心抽象：

- **输入**：业务表单 + 附件。
- **规则引擎**：业务管理员配置的检查项。
- **AI 推理**：大模型执行检查。
- **输出**：结论 + 置信度 + 依据。
- **人机协同**：人类做最终决策，系统学习人类反馈。

## 五、最小可演示版本（MVP）

建议先做：

1. **一个审批类型**：病假审批（证据单一，规则清晰）。
2. **三个状态**：通过 / 拒绝 / 补材料。
3. **一个配置页面**：业务管理员配置病假需要上传什么。
4. **一个审批详情页**：AI 建议显示在人类负责人面前，可一键确认。
5. **日志留痕**：AI 为什么给出这个结论，必须能查到。
