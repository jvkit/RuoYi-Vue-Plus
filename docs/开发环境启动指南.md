# 开发环境启动指南（RuoYi 两套版本）

本机同时维护**两套 RuoYi-Vue-Plus**，启动前先分清是哪一套：

| 版本 | 后端目录 | 前端目录 | 用途 |
|---|---|---|---|
| **5.6.2**（旧/生产参考） | `RuoYi-Vue-Plus/` | `plus-ui/` | 原生产、截图/参考 |
| **6.0.0**（新/采购迁移） | `ruoyi-6x/` | `plus-ui-6x/` | 采购模块已迁移于此，**当前主推** |

两套端口、数据库完全隔离，可并行跑，也可只起一套。

---

## 一、6.0.0（推荐，采购模块在这里）

### 1. 后端（端口 8091，库 `ry-vue-6x`）
```bash
# 首次或代码改动后需先构建
cd ~/workspace/oa/ruoyi-6x
bash ./mvnw -pl ruoyi-admin -am package -DskipTests

# 启动
cd ~/workspace/oa/ruoyi-6x/ruoyi-admin
nohup java -jar target/ruoyi-admin.jar > /tmp/ruoyi-6x.log 2>&1 &
# 健康检查
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8091/   # 期望 200
```
- 端口、库、Redis 已在 `application.yml`/`application-dev.yml` 配好（无需带参数）。
- MySQL `ry-vue-6x`（root/root）、Redis 密码 `ruoyi123`。
- 登录：`admin` / `admin123`，**无租户**。
- 已关闭接口加密（`api-decrypt.enabled=false`）与验证码（`captcha.enable=false`），联调方便。

### 2. 前端（dev 端口 8082，实际可能 8083）
```bash
cd ~/workspace/oa/plus-ui-6x
pnpm install          # 首次
nohup pnpm dev > /tmp/plus-ui-6x-dev.log 2>&1 &
```
- 访问 `http://127.0.0.1:8083`（若 `8082` 被残留进程占用，vite 自动用 8083）。
- dev 代理 `/dev-api` → `http://127.0.0.1:8091`。

## 二、5.6.2（旧版，截图/参考用）

### 1. 后端（端口 8088，库 `ry-vue`）
```bash
cd ~/workspace/oa/RuoYi-Vue-Plus/ruoyi-admin
nohup java -jar target/ruoyi-admin.jar --server.port=8088 > /tmp/ruoyi-admin.log 2>&1 &
```
- 登录 `admin` / `admin123`，**租户号 `000000`**（5.6.2 是多租户）。

### 2. 前端 —— ⚠️ 用 dev server（8081），不要用 nginx（8090）
```bash
cd ~/workspace/oa/plus-ui
nohup pnpm dev > /tmp/plus-ui-dev.log 2>&1 &
```
- 访问 `http://127.0.0.1:8081`。
- 登录：`admin` / `admin123`，租户 `000000`。

> **重要坑（已踩）**：不要用 `http://127.0.0.1:8090`（nginx 容器跑的生产构建）登录。生产构建开启接口加密，但 nginx 代理时会把加密标识头 `encrypt-key` 丢调，后端收到的是加密字符串却按明文解析，报 `Cannot construct instance of LoginBody`，登录必失败。要用就用 dev（8081，不加密）。

## 三、停止

```bash
# 停止某套后端：找对应 java 进程 kill
ss -ltnp | grep -E "8091|8088"    # 看 PID
kill <PID>

# 停止某套前端 dev：找 pnpm/node 进程
ss -ltnp | grep -E "8083|8081"
kill <PID>
```

## 四、常用端口速查

| 端口 | 服务 | 说明 |
|---|---|---|
| 8091 | 6x 后端 | 采购迁移版 |
| 8083 | 6x 前端 dev | 8082 被占则用 8083 |
| 8088 | 5.6.2 后端 | 旧版 |
| 8081 | 5.6.2 前端 dev | 旧版（推荐） |
| 8090 | nginx 前端 | 旧版生产构建，**登录有加密坑** |
| 8080 | 系统 python | 被占用，勿用 |

## 五、常见坑汇总

1. **5.6.2 登录失败**（`LoginBody` 反序列化错误）→ 用 dev `8081`，别用 nginx `8090`。
2. **6x 登录 403** → 缺 `clientid` 请求头；6x 请求需带 `clientid: e5cd7e4891bf95d1d19206ce24a7b32e`（浏览器前端自动带，curl 手动要加）。
3. **接口加密**：6x 前后端都已关；5.6.2 dev 关、nginx 生产开（不匹配见坑 1）。
4. **验证码**：6x 已关；5.6.2 dev 默认关。
5. **租户**：5.6.2 登录要 `000000`；6x 无租户。
6. **数据库**：别改错库——5.6.2 用 `ry-vue`，6x 用 `ry-vue-6x`。
7. **构建**：6x 用 `bash ./mvnw`（不要直接 `mvn`，本机 Maven 3.6.3 偏旧）；5.6.2 后端 jar 需 `mvn package` 重新生成。

## 六、迁移相关（补充背景）

采购模块已从 5.6.2 迁移到 6.0.0，详见 `docs/采购模块6X迁移报告.md`。6x 后端 `8091` + 前端 `8083` 即采购迁移版运行环境，采购相关开发请在此环境进行。
