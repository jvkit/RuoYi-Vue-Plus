# 权限与菜单设计

## 1. RuoYi 的权限模型

### 1.1 用户 → 角色 → 菜单（权限）

- 一个用户可以绑定多个角色。
- 一个角色可以绑定多个菜单/按钮。
- **用户最终能看到的菜单 = 所有角色绑定菜单的并集**。
- **用户最终拥有的权限码 = 所有角色绑定菜单的 perms 并集**。

> 坑点：如果某个审批角色 historically 绑了一整套采购菜单，那么只要用户同时拥有这个审批角色 + `common_user`，并集后就会看到很多不该看的菜单。

### 1.2 superadmin 特判机制

RuoYi 在多处用 `LoginHelper.isSuperAdmin(userId)` 判断是否超管：

```java
public static boolean isSuperAdmin(Long userId) {
    return SystemConstants.SUPER_ADMIN_USER_ID.equals(userId);
}
```

- `SUPER_ADMIN_USER_ID = 1761100000000000001L`，即内置 admin 用户。
- **只认用户 ID，不认 `superadmin` 角色**。
- 所以给李迪分配 `superadmin` 角色后，他默认仍然不会获得全部菜单/全部权限。

#### 解决方案

不要改 `LoginHelper.isSuperAdmin()`（登录流程在虚拟线程执行时 `SaTokenContext` 未初始化，读会话会炸）。

在需要按角色判断超管的服务层（`SysMenuServiceImpl`、`SysPermissionServiceImpl`、`SysUserServiceImpl`）增加数据库层面的角色校验：

```java
private boolean isSuperAdminUser(Long userId) {
    if (LoginHelper.isSuperAdmin(userId)) {
        return true;
    }
    return roleMapper.selectRolesByUserId(userId).stream()
        .anyMatch(SysRoleVo::isSuperAdmin);
}
```

这样持有 `superadmin` 角色的用户（如李迪）也能：
- 看到全部菜单；
- 拥有 `*:*:*` 全部权限码；
- 在界面上分配/保留 `superadmin` 角色。

## 2. 角色职责分离（推荐设计）

### 2.1 两类角色

| 角色类型 | 例子 | 用途 | 是否绑菜单 |
|---|---|---|---|
| 显示角色 | `common_user`（普通用户） | **唯一控制用户能看到哪些菜单** | 绑菜单 |
| 审批角色 | `team_leader`、`dept_leader`、`warehouse_admin` | **只用于 Warm-Flow 审批节点找人** | **不绑任何菜单** |

### 2.2 为什么必须分离

- 如果审批角色也绑菜单，用户同时绑多个角色时，菜单并集会把所有审批角色的菜单都显示出来。
- 后果：普通用户看到供应商管理、BOM、订单、合同、报销等未开放页面。

### 2.3 清理脚本示例

```sql
DELETE FROM sys_role_menu
WHERE role_id IN (
    @role_team_leader,
    @role_dept_leader,
    @role_acceptance_contact,
    @role_warehouse_admin
);
```

> 注意：只删 `sys_role_menu`，不删角色本身，否则流程节点找不到审批人。

## 3. 普通用户菜单最小集（当前实践）

普通用户 `common_user` 当前可见：

- 首页
- PRIME AI
- 我的任务（含我的待办/已办/抄送/我发起的）
- 工作流 → 流程定义（只看，不管理）
- 采购管理 → 采购申请 / 采购验收 / 仓库库存 / 领用申请
- 手机端专属 → 移动验收
- 文件上传/下载

不可见：
- 项目管理（但保留 `项目树选择` 按钮权限，供采购申请表单使用）
- 发票台账
- 流程监控 / 流程实例
- 供应商、BOM、订单、合同、报销、资金等

## 4. 按钮权限必须单独绑定

页面上的按钮用 `v-hasPermi="['xxx:xxx:xxx']"` 控制显示，但后端接口用 `@SaCheckPermission("xxx:xxx:xxx")` 控制访问。**按钮权限也需要在 `sys_menu` 里存在，并绑到角色**。

### 踩坑案例：采购申请提交

列表操作列有「提交」按钮：

```vue
<el-button v-hasPermi="['procurement:request:submit']" ... />
```

后端接口：

```java
@SaCheckPermission("procurement:request:submit")
@PostMapping("/submit")
```

如果 `sys_menu` 里没有 `procurement:request:submit` 这个按钮菜单，或没有绑给 `common_user`，普通用户点击提交就会报：

> 没有访问权限，请联系管理员授权

### 按钮菜单创建示例

```sql
INSERT IGNORE INTO sys_menu (
    menu_id, menu_name, parent_id, order_num, path, component,
    menu_type, visible, status, perms, icon
) VALUES (
    1801047, '采购申请提交', 1801040, 6, '#', NULL,
    'F', '0', '0', 'procurement:request:submit', '#'
);

INSERT IGNORE INTO sys_role_menu (role_id, menu_id)
VALUES (@role_common_user, 1801047);
```

## 5. 隐藏菜单用于路由跳转

「我的任务」点击办理/查看时，会按 `flow_definition.form_path` 跳转，例如 `/procurement/request/detail`。这种详情页需要：

1. 前端组件存在：`src/views/procurement/request/detail.vue`。
2. `sys_menu` 里挂一条**隐藏菜单**（`visible='1'`），`component` 对应详情页路径。
3. 角色绑定这条隐藏菜单，否则跳转 404。

示例：流程设计详情页

```sql
INSERT IGNORE INTO sys_role_menu (role_id, menu_id)
VALUES (@role_common_user, 1761400000000011700); -- 流程设计
```

## 6. 父菜单可见性与子按钮权限解耦

普通用户不需要看到「项目管理」菜单，但采购申请表单里需要调用 `/procurement/project/tree`。做法：

- 对普通用户隐藏「项目管理」菜单（`1801010`）和「项目管理查询」按钮（`1801011`）。
- **保留**「项目树选择」按钮（`1801016`）的权限绑定。

因为 `@SaCheckPermission("procurement:project:tree")` 只检查用户是否拥有该权限码，与父菜单是否可见无关。

## 7. 超管分配角色的注意事项

`SysUserServiceImpl.insertUserRole` 原有逻辑：

```java
if (!LoginHelper.isSuperAdmin(userId)) {
    roleList.remove(SystemConstants.SUPER_ADMIN_ROLE_ID);
}
```

这里判断的是**被编辑用户**是否为硬编码超管，导致无法给李迪这类角色超管分配角色。

改为判断**当前操作人**是否为超管（含角色）：

```java
if (!isSuperAdminUser(LoginHelper.getUserId())) {
    roleList.remove(SystemConstants.SUPER_ADMIN_ROLE_ID);
}
```

## 8. OSS 附件读取权限

审批人查看申请人上传的附件（付款截图、报价单、发票等）时，前端会调 `/resource/oss/listByIds/{ossIds}` 获取文件真实 URL。该接口原需 `system:oss:query`，而审批角色通常只有 `common_user`，没有此权限，导致详情页图片/附件加载失败并提示「没有访问权限」。

### 处理方式

最简方案：对「读」类 OSS 接口取消按钮级权限校验，保留登录校验。具体修改 `SysOssController`：

- `/resource/oss/listByIds/{ossIds}`：移除 `@SaCheckPermission("system:oss:query")`
- `/resource/oss/download/{ossId}`：移除 `@SaCheckPermission("system:oss:download")`

上传（`/upload`）、列表（`/list`）、删除（`/{ossIds}`）仍保留权限控制，避免任意用户都能管理文件。

> 注意：这只是放开 RuoYi 层的权限校验。如果 MinIO/OSS 本身对文件 URL 做了签名或私有桶限制，还需要在 OSS 服务端配置公开访问或预签名策略。

## 9. 快速诊断权限问题

1. 先看 `sys_user_role` 确认用户有哪些角色。
2. 再看 `sys_role_menu` 确认这些角色绑了哪些菜单。
3. 浏览器 Network 里看 `getInfo` 返回的 `permissions` 是否包含目标权限码。
4. 后端日志里看具体哪个 `@SaCheckPermission` 拦截了请求。
5. 图片/附件 403 时，重点查 `/resource/oss/listByIds` 和 `/resource/oss/download`。
