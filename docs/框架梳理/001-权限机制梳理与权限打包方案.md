# 001 权限机制梳理与权限打包方案

> 角标：001  
> 阶段：只讨论，不改动代码  
> 目标：把 RuoYi 权限机制彻底讲清楚，回答"职位能干啥""能不能事务权限""能不能权限打包"三个疑问。

---

## 一、先说结论

1. **RuoYi 不只有部门和角色**，它还有**岗位（post）**、**用户**、**SpEL 表达式**五种办理人方式，但这些主要是在**工作流审批**里用。
2. **菜单/按钮的功能权限只认角色**，岗位不能直接控制"你能不能看到某个页面"。
3. **数据权限** RuoYi 原生按部门过滤，但我们的业务需要按项目过滤，所以这部分要自己写。
4. **"权限打包"这个诉求，角色本身就是打包**。如果嫌角色粒度太细，可以再加一层"岗位-角色映射"或"角色组"。
5. **采购申请的"提交"按钮不能简单无权化**。如果每个人都应该能提交，那就需要一个默认角色（或默认权限包）自动赋给所有人；否则流程确实会卡住。

---

## 二、RuoYi 权限机制全景

RuoYi 的权限分三块，机制各不相同：

```
┌─────────────────────────────────────────────────────────────┐
│  ① 功能权限：谁能看到哪个页面、点哪个按钮                          │
│     → 控制单位：sys_menu（菜单/按钮）                            │
│     → 分配方式：通过 sys_role_menu 把菜单分配给角色                │
│     → 校验方式：前端 v-hasPermi，后端 @SaCheckPermission         │
│     → 只支持角色，不支持岗位/部门                                 │
├─────────────────────────────────────────────────────────────┤
│  ② 数据权限：能看到哪些数据行                                     │
│     → 控制单位：sys_role.data_scope                              │
│     → 分配方式：给角色设置数据范围 + sys_role_dept 自定义部门      │
│     → 校验方式：@DataScope + PlusDataPermissionHandler           │
│     → 原生按 dept_id 过滤，不支持项目/岗位                         │
├─────────────────────────────────────────────────────────────┤
│  ③ 流程办理人：审批任务派给谁                                     │
│     → 控制单位：flow_definition 节点上的 permission_flag          │
│     → 支持 5 种：user: / role: / dept: / post: / ${SpEL}         │
│     → 由 WorkflowPermissionHandler + FlwTaskAssigneeService 解析 │
└─────────────────────────────────────────────────────────────┘
```

下面逐层展开。

---

## 三、功能权限：只认角色

### 3.1 怎么工作的

- 菜单表 `sys_menu` 里每个菜单/按钮有一个 `perms` 字段，例如：
  - `procurement:request:list`：查看采购申请列表
  - `procurement:request:add`：打开新增表单
  - `procurement:request:submit`：提交申请
- 角色表 `sys_role` 通过 `sys_role_menu` 关联到菜单。
- 用户通过 `sys_user_role` 关联到角色。
- 后端接口加 `@SaCheckPermission("procurement:request:add")`，没角色就返回 403。
- 前端按钮加 `v-hasPermi="['procurement:request:add']"`，没角色按钮不显示。

### 3.2 岗位为什么不能控制功能权限

- `sys_post`（岗位表）只有 `post_id`、`dept_id`、`post_code`、`post_name` 等字段。
- RuoYi 没有 `sys_post_menu` 或 `sys_post_role` 这种关联表。
- 所以岗位目前只是人事档案，和权限菜单没有直接关系。

**但岗位是可以扩展的**：如果我们加一张 `sys_post_role` 映射表，就可以让"岗位 = 一组角色的打包"。这是后面要讨论的"权限打包"方案之一。

## 四、数据权限：原生按部门，我们需要按项目

### 4.1 RuoYi 原生数据权限

`DataScopeType` 枚举定义了 6 种数据范围（代码位置：`ruoyi-6x/ruoyi-common/ruoyi-common-mybatis/src/main/java/org/dromara/common/mybatis/enums/DataScopeType.java`）：

| code | 类型 | 含义 |
|---|---|---|
| 1 | ALL | 全部数据 |
| 2 | CUSTOM | 自定义数据（角色关联的部门） |
| 3 | DEPT | 本部门数据 |
| 4 | DEPT_AND_CHILD | 本部门及以下数据 |
| 5 | SELF | 仅本人数据 |
| 6 | DEPT_AND_CHILD_OR_SELF | 本部门及以下或本人 |

`@DataScope` 注解会自动在 SQL 里拼 `dept_id` 条件。例如当前用户角色是"本部门"，查询时会自动加上 `WHERE dept_id = 当前用户部门ID`。

### 4.2 为什么我们不适合直接用

- 我们的数据过滤维度是**项目**，不是部门。
- `pms_procurement_request`、`pms_acceptance`、`pms_issue_request` 这些表里没有 `dept_id` 字段，有的是 `project_id`。
- 如果硬用 `@DataScope`，需要把项目映射成"虚拟部门"，很别扭。

### 4.3 建议做法

**不用 `@DataScope`，自己写一个项目级数据权限工具**：

```java
// 伪代码
public class ProcurementDataScopeUtil {
    public List<Long> getVisibleProjectIds() {
        // 1. admin 返回全部
        // 2. 项目负责人返回自己负责的项目
        // 3. 普通用户返回自己参与过的项目（create_by / 申请人 / 验收人 / 领用人）
        // 4. 仓库管理员等特殊角色返回全部
    }
}
```

在每个列表查询 Service 里显式拼接：

```java
queryWrapper.in("project_id", visibleProjectIds)
            .or().eq("create_by", currentUserId);
```

这样比强行套 `@DataScope` 更清晰，也更好测试。

## 五、流程办理人：这才是 RuoYi 最强的地方

### 5.1 五种办理人方式

代码位置：`ruoyi-6x/ruoyi-modules/ruoyi-workflow/src/main/java/org/dromara/workflow/common/enums/TaskAssigneeEnum.java`

| 类型 | 前缀 | 示例 | 含义 |
|---|---|---|---|
| 用户 | 无或 `user:` | `user:100` 或 `100` | 指定某个人 |
| 角色 | `role:` | `role:5` | 拥有该角色的所有人 |
| 部门 | `dept:` | `dept:3` | 该部门的所有人 |
| 岗位 | `post:` | `post:4` | 该岗位的所有人 |
| SpEL 表达式 | `${}` 或 `#{}` | `${leaderId}` | 动态取流程变量 |

解析代码在 `FlwTaskAssigneeServiceImpl.fetchUsersByStorageIds()` 里，会把 `role:5` 展开成所有拥有角色 5 的用户列表。

### 5.2 岗位在这里有大用

岗位（post）虽然不能控制菜单权限，但**可以控制审批任务派给谁**。

例如：

- 岗位 "团队上级" 映射到 `post:10`
- 流程节点配 `permission_flag = post:10`
- 所有被设为 "团队上级" 岗位的人都会收到审批任务

这比角色更贴近人事结构。因为：

- **角色是权限集合**（你能干啥）。
- **岗位是职责身份**（你是谁）。

一个人可以有多个岗位，也可以换岗位而不换账号。

### 5.3 当前我们的流程为什么用角色

因为我们之前创建了 `team_leader`、`dept_leader`、`warehouse_admin` 这些角色，并且把它们同时用于：

1. 菜单权限（让这些人能看到审批页面）。
2. 流程办理人（让任务派到这些人）。

这其实把"角色"和"岗位"混用了。更好的做法是：

- **用角色控制功能权限**（谁能打开审批页面）。
- **用岗位控制流程办理人**（任务派给谁）。

当然也可以继续用角色，只是语义上不够干净。

## 六、回答你的具体问题

### 6.1 "RuoYi 只有通过部门与角色来管控权限吗？感觉有点垃圾"

**不是只有部门和角色**。完整看：

- 功能权限：只支持角色。
- 数据权限：原生支持角色 + 部门。
- 流程办理人：支持用户、角色、部门、岗位、SpEL 表达式。

说"垃圾"有点冤枉，因为这是典型的 RBAC 设计，适合大多数中后台。但对我们这种**项目驱动**的业务，它确实在数据权限上不够灵活，需要我们自己扩展。

### 6.2 "职位是干啥的？支持其他方式吗？"

- **职位/岗位（post）**：RuoYi 里主要是人事档案，目前没被权限系统使用。但 Warm-Flow 的审批节点可以直接用 `post:` 前缀指派任务。
- **其他方式**：
  - 用户 `user:`：硬编码指定某个人。
  - 角色 `role:`：指定某类人。
  - 部门 `dept:`：指定某个部门的人。
  - SpEL `${变量}`：动态指定，如 `${leaderId}`（项目负责人）、`${applicantId}`（申请人）。

对于我们的业务，**SpEL + 岗位** 是最灵活的：

- 项目负责人用 `${leaderId}` 动态取。
- 团队上级、部门上级、仓库管理员用 `post:`。
- 特殊审批人用 `user:` 或 `role:`。

### 6.3 "能不能不操作角色权限，而是操作事务权限？"

可以，但需要自己实现。**事务权限（或对象级权限）**的意思是：权限不是绑在人身上，而是绑在业务对象上。

例如：

- "这个项目允许谁审批"
- "这张采购单允许谁查看"
- "这个验收单允许谁操作"

实现方式是在业务表里加权限字段，例如：

```sql
pms_project
  - leader_id          -- 项目负责人
  - viewer_user_ids    -- 可见用户（JSON 数组）
  - viewer_role_ids    -- 可见角色（JSON 数组）
```

查询时判断：

```java
if (userId == project.leaderId 
    || project.viewerUserIds.contains(userId)
    || userRoles.intersect(project.viewerRoleIds)) {
    // 可见
}
```

**优点**：

- 权限和业务对象强绑定，非常灵活。
- 适合项目制组织。

**缺点**：

- 每个查询都要自定义判断，工作量大。
- 权限分散在各业务表里，不好统一审计。
- 和 RuoYi 原生的 `@SaCheckPermission`、`@DataScope` 不兼容。

**我的建议**：

- 不全面转向事务权限，成本太高。
- 在 RuoYi 角色权限基础上，**补充项目级数据权限**（按 `project_id` 过滤）。
- 特殊场景（如项目负责人）用业务字段 `leader_id` 来识别。

### 6.4 "采购申请按钮如果无权化会怎样？"

如果你把 `procurement:request:submit` 从所有角色里移除，会出现两种情况：

1. ** nobody 能提交**：所有用户点提交都报 403，系统变成只读。
2. **绕过权限校验**：后端接口不加 `@SaCheckPermission`，所有人都能调接口提交。但前端按钮可能隐藏，体验不一致。

你担心的"如果这个人未关联任何角色，程序也不知道流程怎么走"，这其实是两个问题：

- **能不能提交**：是功能权限问题，应该让所有人（或至少所有登录用户）都能提交。
- **流程怎么分派**：是流程办理人问题，取决于节点配置的是 role / post / user / SpEL。

所以正确的做法不是"无权化"，而是：

- 给所有用户一个**默认角色**，包含 `procurement:request:submit` 等基础权限。
- 流程节点用 role / post / SpEL 明确指定审批人。
- 保证每个审批角色/岗位至少有一个用户。

### 6.5 "可以把角色权限打包吗？把一堆权限打包，然后分配给一个对象"

**角色本身就是一种权限打包**。一个角色 = 一组菜单/按钮权限的集合。

如果你觉得角色还不够，想要更高层级的打包，有三种方案：

#### 方案 A：多角色（最简单，推荐）

一个用户关联多个角色。

例如王建龙：
- 角色 A：common_user（基础面板）
- 角色 B：team_leader（团队上级审批）
- 角色 C：project_manager（项目负责人数据权限）

**优点**：RuoYi 原生支持，无需改代码。
**缺点**：用户角色多的时候管理略繁琐。

#### 方案 B：岗位-角色映射（语义最干净）

加一张 `sys_post_role` 表：

```sql
sys_post_role
  - post_id
  - role_id
```

岗位 = 一组角色。给用户分配岗位，就自动获得该岗位下的所有角色。

例如：

| 岗位 | 自动获得角色 |
|---|---|
| 团队上级 | common_user + team_leader + project_manager |
| 部门上级 | common_user + dept_leader + project_manager |
| 仓库管理员 | common_user + warehouse_admin |

**优点**：

- 人事变动时，只需改用户岗位，不用改角色。
- "岗位"和"角色"职责分离：岗位是身份，角色是权限包。

**缺点**：

- 需要改 RuoYi 用户管理逻辑，创建/更新用户时自动同步角色。
- 需要维护岗位-角色映射。

#### 方案 C：角色组（最灵活）

加一张 `sys_role_group` 和 `sys_role_group_role` 表：

```sql
sys_role_group
  - group_id
  - group_name    -- 如"采购审批组""仓库管理组"

sys_role_group_role
  - group_id
  - role_id
```

用户关联角色组，就获得该组下所有角色。

**优点**：

- 可以把相关角色打包，比如"采购审批组"包含 team_leader、dept_leader、acceptance_contact。
- 适合批量赋权。

**缺点**：

- 比方案 A 多一层抽象，复杂度更高。
- RuoYi 登录时只认 `sys_user_role`，需要改登录逻辑把角色组展开成角色。

### 6.6 我的推荐

| 场景 | 推荐方式 |
|---|---|
| 基础功能（提交申请、查看自己的单据） | 多角色：给所有用户关联 `default_user` |
| 审批任务分派 | Warm-Flow 的 `post:` 或 `role:` 或 `${SpEL}` |
| 数据权限（能看到哪些项目） | 自定义项目级过滤 |
| 人事变动频繁、岗位明确 | 未来可扩展"岗位-角色映射" |
| 批量赋权 | 未来可扩展"角色组" |

**当前阶段建议先用方案 A（多角色）**，因为 RuoYi 原生支持，改动最小。等人员规模变大、岗位稳定后，再引入方案 B（岗位-角色映射）。

## 七、针对我们系统的具体建议

### 7.1 角色设计

保留并明确以下角色：

| 角色 | 功能权限 | 数据权限 | 流程用途 |
|---|---|---|---|
| `default_user` | 我的任务、采购申请/验收/领用的基础操作 | 看自己的 + 自己项目的 | 无 |
| `project_manager` | 项目管理 | 看自己的项目 | 作为项目负责人审批 |
| `team_leader` | 审批页面 | 看自己审批的 | 采购申请 < 1000 审批 |
| `dept_leader` | 审批页面 | 看自己审批的 | 采购申请 ≥ 1000 审批 |
| `warehouse_admin` | 仓库管理、领用审批 | 看全部库存 | 领用审批 |
| `admin` | 全部 | 全部 | 代审批 |

所有新用户自动关联 `default_user`。

### 7.2 岗位设计（可选，建议后续引入）

| 岗位 | 对应角色（岗位-角色映射） |
|---|---|
| 团队上级 | team_leader + project_manager + default_user |
| 部门上级 | dept_leader + project_manager + default_user |
| 仓库管理员 | warehouse_admin + default_user |
| 普通员工 | default_user |

这样以后人事入职，只需要设岗位，角色自动带出来。

### 7.3 流程节点配置

| 节点 | 办理人配置 | 说明 |
|---|---|---|
| 采购申请 - 项目负责人 | `${leaderId}` | 根据 project.leader_id 动态取 |
| 采购申请 - 团队上级 | `post:team_leader_id` 或 `role:team_leader_id` | 金额 < 1000 |
| 采购申请 - 部门上级 | `post:dept_leader_id` 或 `role:dept_leader_id` | 金额 ≥ 1000 |
| 验收 - 采购申请人 | `${applicantId}` | 原申请提交人 |
| 验收 - 项目负责人 | `${leaderId}` | 项目 leader |
| 验收 - 团队上级 | `post:team_leader_id` 或 `role:team_leader_id` | 统一走团队上级 |
| 领用 - 仓库管理员 | `post:warehouse_admin_id` 或 `role:warehouse_admin_id` | 仓库审批 |

### 7.4 数据权限规则

```
用户可见数据 = 
  admin: 全部
  warehouse_admin: 全部库存 + 自己相关的领用
  project_manager: 自己负责的项目及其下的申请/验收/领用
  普通用户: 自己 create_by 的单据 + 自己项目下的单据
```
