# 010 - OA 采购系统框架设计初版

> 目标：在现有 RuoYi + 采购模块基础上，输出一版可评审、可落地的框架设计。
>
> 本文档包含：已明确的决策、推荐的最优设计、待确认的不确定点。

---

## 一、设计目标

1. **跑通核心流程**：采购申请 → 审批 → 验收 → 入库 → 领用。
2. **权限不硬编码**：不把所有审批人、可见范围都绑死在角色上。
3. **流程与业务解耦**：工作流只负责流转，业务状态由业务代码维护。
4. **可扩展**：后续能接 BOM、合同、报销、AI、中心 OA，而不需要推翻现有结构。
5. **先能用，再好用**：第一周上线自己用，后续再优化权限、AI、报表。

## 二、已明确的决策（不再讨论）

### 2.1 项目与采购

| 项 | 决策 |
|---|---|
| 项目 | 多级树形，预算父子约束（子 ≤ 父），无层级限制 |
| 项目归属 | 长三角/北京/天目湖等为"资金来源/部门"，项目挂在下面 |
| 采购申请标题 | 自动生成：`【自购/对公】+ 项目名 + MM月DD日 + 名称`，导出 Excel 用 |
| 采购编码 | 自动生成：`req-YYYYMMDD-000` |
| 项目编码 | 自动生成：`proj-YYYYMMDD-000` |
| 采购种类 | 申请表单上选「科研/非科研」，明细不再重复选 |
| 采购分类 | 树形单选，一二级合并，直接选叶子节点 |
| 采购订单 | 不保留游离订单页面，明细挂在采购申请下 |
| 供应商 | 暂不管理，明细保留供应商字段 |

### 2.2 审批流程

| 流程 | 节点 |
|---|---|
| 采购申请 | 申请人提交 → 项目负责人 → 金额分支（<1000 团队上级，≥1000 部门上级）→ 结束 |
| 采购验收 | 验收人提起 → 原采购申请人 → 项目负责人 → 团队上级 → 结束 → 自动入库 |
| 领用申请 | 申请人提交 → 仓库管理员 → 结束 → 扣减库存 |

说明：
- 当前先用**链式审批**（串行），简单可预期。
- 审批人优先按**角色**配置，但流程变量支持动态指定（如 `${applicantId}`）。

### 2.3 人员角色（当前阶段）

| 角色 | 用途 |
|---|---|
| 普通用户 | 提交采购/验收/领用申请 |
| 团队上级 | 审批 < 1000 的采购申请 |
| 部门上级 | 审批 ≥ 1000 的采购申请 |
| 仓库管理员 | 审批领用申请、管理库存 |
| 系统管理员 | 管理项目、用户、菜单、流程 |

> 后续逐步弱化"角色硬编码"，但当前阶段保留角色作为流程审批锚点。

## 三、推荐的最优设计

### 3.1 权限模型：从"角色唯一"改为"多维权限"

当前问题：所有权限都绑角色，导致普通用户看不到菜单、提交不了申请。

推荐方案：

```
权限 = 功能权限 ⊕ 数据权限 ⊕ 流程权限
```

#### 3.1.1 功能权限（能不能点）

由**菜单 + 按钮权限字符**控制，绑定到角色。

| 功能 | 默认分配给 |
|---|---|
| 提交采购申请 | 普通用户 |
| 提交验收申请 | 普通用户 |
| 提交领用申请 | 普通用户 |
| 审批采购申请 | 团队上级 / 部门上级 |
| 审批验收申请 | 原申请人 / 项目负责人 / 团队上级 |
| 审批领用申请 | 仓库管理员 |
| 管理项目 | 系统管理员 |
| 查看全部数据 | 系统管理员 |

> 关键改动：把"提交申请"这类基础能力，默认分配给所有登录用户（或一个默认角色），不再只有 admin 能用。

#### 3.1.2 数据权限（能看到哪些）

| 维度 | 说明 |
|---|---|
| 全部 | 管理员 |
| 所属项目 | 项目负责人可见自己项目的采购/验收/库存 |
| 自己提交 | 普通用户默认可看自己提交的申请 |
| 自己审批 | 审批人可见流到自己节点的记录 |
| 仓库维度 | 仓库管理员可见全部库存 |

> 第一阶段建议**不过滤数据**，让所有人可见。第二阶段再按项目/提交人/审批人做数据范围控制。

#### 3.1.3 流程权限（谁审批）

流程节点里不直接写死用户名，而是写**规则表达式**：

| 节点 | 规则 |
|---|---|
| 项目负责人 | `${projectLeaderId}`（选择项目时带出） |
| 原采购申请人 | `${applicantId}`（从关联采购申请取 create_by） |
| 团队上级 | `role:team_leader` |
| 部门上级 | `role:dept_leader` |
| 仓库管理员 | `role:warehouse_admin` |

> 这样以后组织结构调整时，只需换角色上绑的人，不用改流程定义。

### 3.2 流程与业务解耦

核心原则：

> **Warm-Flow 只负责"把任务推给谁"和"流转"，业务表只记录"业务状态"和"关联的流程实例 ID"。**

#### 3.2.1 业务状态机

每个业务实体有自己的状态，不直接用 Warm-Flow 的 task 状态替代。

**采购申请状态：**

```
DRAFT（草稿）
  → SUBMITTED（已提交，审批中）
  → APPROVED（审批通过）
  → REJECTED（被驳回）
  → REVOKED（撤回）
```

**验收单状态：**

```
DRAFT
  → SUBMITTED
  → APPROVED
  → REJECTED
```

同时，采购申请本身增加验收标志：

```
acceptance_status: none / processing / done
```

#### 3.2.2 流程钩子

在流程关键节点回调业务代码：

| 事件 | 业务动作 |
|---|---|
| 采购申请审批通过 | 扣减项目预算、生成资金流出记录、允许创建验收单 |
| 采购申请被驳回 | 回滚预算占用 |
| 验收单审批通过 | 物料入库、修改采购申请验收标志为 done |
| 领用单审批通过 | 扣减库存 |

> 这些回调通过 Warm-Flow 的监听器或 Service 层主动调用来实现。

### 3.3 模块划分

```
oa-procurement（采购业务模块）
├── project（项目管理）
├── request（采购申请 + 明细）
├── acceptance（采购验收 + 发票/图片）
├── warehouse（仓库/库存）
├── issue（领用申请）
├── fund（资金管理/资金流水）
├── bom（BOM 库 + BOM 表）
├── contract（合同模板与生成）
├── reimbursement（报销导出与打包）
└── workflow（流程监听与业务钩子）
```

> 第一阶段只实现前 6 个模块（project/request/acceptance/warehouse/issue/fund）。

## 四、不确定点与建议

| 不确定点 | 建议方案 | 备注 |
|---|---|---|
| 部门与项目的归属关系 | 项目表保留 `dept_id` 字段，但只作为分类/资金来源，不做强权限控制 | 后续需要时再升级 |
| 组织结构和审批人分配 | 第一阶段继续用角色，第二阶段引入部门负责人、职位等动态规则 | 角色简单，够用 |
| 资金管理的粒度 | 采购申请审批通过时记一笔「实际支出」流水 | 先做支出，再做预算占用 |
| 数据权限严格程度 | 第一阶段不过滤，所有人可见全部数据 | 避免普通用户看到"无权"错觉 |
| 是否需要多租户 | 否 | 当前 RuoYi 6x 已移除多租户 |
| 与中心 OA/泛微对接 | 二阶段再考虑 | 先保证内部流程跑通 |
| AI 集成位置 | 二阶段：采购链接抓取价格、发票 AI 初审、BOM 完善 | 先实现传统表单 |
| 合同/报销模块 | 二阶段 | 依赖验收和入库数据 |

## 五、实施路线图

### 第一阶段（本周目标）：跑通主链路

1. 修复权限：普通用户可提交申请，不显示"无权"。
2. 完善采购申请流程：申请人 → 项目负责人 → 金额分支 → 结束。
3. 完善验收流程：验收人 → 原申请人 → 项目负责人 → 团队上级 → 结束 → 入库。
4. 完善领用流程：申请人 → 仓库管理员 → 结束 → 扣库存。
5. 项目资金管理：采购通过时记录资金流出，校验剩余预算。
6. 修复已知 bug：重复验收、时间显示、字段缺失、审批查看权限等。

### 第二阶段：数据权限与易用性

1. 按项目/提交人/审批人过滤数据。
2. 移动端验收页面优化。
3. 导出中心 Excel 模板。
4. 流程驳回后重新提交的完整闭环。

### 第三阶段：BOM、合同、报销

1. BOM 库与 BOM 表管理。
2. 合同模板生成。
3. 报销打包导出（申请表 + 验收图 + 发票）。

### 第四阶段：AI 与外部对接

1. AI 抓取采购链接价格。
2. 发票 AI 初审。
3. 接入中心 OA/泛微。

## 六、关键设计原则再强调

1. **流程定义只描述流转规则，不写业务逻辑。**
2. **业务表必须有独立状态，不依赖流程 task 状态。**
3. **审批人尽量用角色/动态变量，不写死用户名。**
4. **基础功能（提交申请）对所有用户开放。**
5. **数据权限先放宽松，后续再收紧。**
6. **每一个数据库改动都固化为 SQL 脚本，保持幂等。**
