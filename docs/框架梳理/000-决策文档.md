# 000 决策文档

> 角标：000（元文档，持续更新）  
> 作用：记录所有前置设计决策，作为后续开发的依据。  
> 更新规则：每做一个决策，按格式追加一条；决策变更时打 `[已变更]` 并说明原因。

---

## 一、决策记录格式

```markdown
### 决策编号 Dxxx：标题

- **状态**：已确认 / 待确认 / 已变更
- **提出时间**：YYYY-MM-DD
- **背景**：为什么需要这个决策
- **结论**：最终决定
- **依据**：引用的文档/规范/讨论
- **影响范围**：哪些模块会受影响
- **实施状态**：未开始 / 进行中 / 已完成
```

### D004：业务状态与流程状态分层

- **状态**：已确认
- **提出时间**：2026-08-25
- **背景**：当前各表状态字段与 Warm-Flow 流程状态混用，容易被覆写。
- **结论**：
  - 流程状态由 Warm-Flow 维护（waiting/finish/back）。
  - 业务状态由各业务表维护（draft/submitted/approved/rejected/completed 等）。
  - 流程事件监听负责把流程状态映射为业务状态。
- **依据**：《前置设计思考与决策讨论.md》问题 3
- **影响范围**：采购申请、验收、领用等所有走流程的表
- **实施状态**：未开始

### D005：新增 `pms_fund_source` 表作为项目归属

- **依据**：《前置设计思考与决策讨论.md》问题 3

- **实施状态**：未开始

### D006：功能权限继续用 RuoYi 原生角色机制

- **状态**：已确认
- **提出时间**：2026-08-26
- **背景**：RuoYi 菜单权限只认角色，岗位/部门不能直接控制菜单。
- **结论**：菜单/按钮功能权限通过 `sys_role` + `sys_role_menu` 分配，后端用 `@SaCheckPermission`，前端用 `v-hasPermi`。
- **依据**：plus-doc 6.X `framework/basic/permissions_control.md`
- **影响范围**：所有菜单、按钮、接口
- **实施状态**：未开始

## 三、待确认决策

### D008：数据权限实现方式

- **状态**：待确认
- **提出时间**：2026-08-26
- **背景**：RuoYi 原生 `@DataScope` 按 `dept_id` 过滤，我们的业务需要按项目过滤。
- **选项**：
  - **A. 使用 RuoYi 原生 `@DataScope`**：把"长三角/天目湖/北京"建成 `sys_dept` 部门，项目 `dept_id` 指向它们。优点：最规范，复用原生能力。缺点：概念上把资金归属当部门。
  - **B. 自定义项目级过滤**：自己写工具类，按 `project_id` / `create_by` / 流程任务过滤。优点：概念清晰。缺点：需要自定义代码，不直接使用 `@DataScope`。
- **推荐**：A（优先遵循 RuoYi 规范）
- **依据**：plus-doc 6.X `framework/basic/permissions.md`
- **影响范围**：数据权限、项目表、所有列表查询
- **实施状态**：未开始

### D009：流程审批人绑定方式

- **状态**：待确认
- **提出时间**：2026-08-26
- **背景**：Warm-Flow 支持 user/role/dept/post/SpEL 五种审批人。
- **选项**：
  - **A. 用 `role:`**：团队上级 / 部门上级 / 仓库管理员都用角色。优点：当前已实现。缺点：角色 = 权限 + 身份，语义不纯。
  - **B. 用 `post:` + `${SpEL}`**：项目负责人用 `${leaderId}`，团队/部门/仓库用岗位。优点：身份和权限分离。缺点：需要维护岗位-人员映射。
- **推荐**：B（长期更干净），但当前可先 A 跑通再迁移到 B。
- **依据**：warm-flow-doc `advanced/variableStategy.md`
- **影响范围**：流程定义 SQL、审批人查找
- **实施状态**：未开始

### D010：流程与业务解耦方式

- **状态**：待确认
- **提出时间**：2026-08-25
- **背景**：当前 `processHandler` 里资金、库存、状态全写在一起。
- **选项**：
  - **A. 引入领域事件**：流程事件发布 `ProcurementApprovedEvent` 等，监听者分别处理资金、库存、通知。
  - **B. 直接 Service 调用**：资金、库存等强一致操作直接调用对应 Service。
- **推荐**：A + B 结合：强一致操作直接调用，弱一致（通知/日志/同步）用事件。
- **依据**：《前置设计思考与决策讨论.md》问题 5
- **影响范围**：Service 层、事件监听、事务边界
- **实施状态**：未开始

### D011：附件存储统一方式

- **状态**：待确认
- **提出时间**：2026-08-25
- **背景**：当前业务表字段附件与 `pms_attachment` 双轨并存。
- **选项**：
  - **A. 全部走 `pms_attachment`**：业务表只保留关键缓存字段。
  - **B. 维持双轨**：简单但后续报销打包困难。
- **推荐**：A
- **依据**：《前置设计思考与决策讨论.md》
- **影响范围**：采购申请、验收、合同、报销
- **实施状态**：未开始

### D012：岗位-角色映射是否引入

- **状态**：待确认
- **提出时间**：2026-08-26
- **背景**：岗位是身份，角色是权限，当前混用。
- **选项**：
  - **A. 当前阶段一个用户挂多个角色**：RuoYi 原生支持，改动最小。
  - **B. 引入 `sys_post_role` 映射**：岗位自动带角色，人事变动只需改岗位。
- **推荐**：A 先行，B 后续视人员规模引入。
- **依据**：《001-权限机制梳理与权限打包方案.md》
- **影响范围**：用户管理、角色管理
- **实施状态**：未开始

## 六、如何更新本文档

1. 新增决策：按格式追加到"已确认决策"或"待确认决策"。
2. 决策确认：从"待确认"移到"已确认"，补充结论和依据。
3. 决策变更：在原决策上打 `[已变更]`，在"已变更决策"中追加新结论。
4. 引用外部文档：优先引用本地 `docs/外部文档/` 路径，其次 URL。
