# 采购系统代码质量评估与前置架构设计

> 本文档用于在继续堆功能之前，先把底层设计共识确认下来。避免"先凑活用，后面越来越难改"。
> 评估范围：`ruoyi-6x/ruoyi-modules/ruoyi-procurement` 及关联 SQL/流程/权限脚本。

---

## 一、总体结论

当前系统已跑通：**采购申请 → 审批 → 验收 → 入库 → 领用** 主链路，代码组织基本遵循 RuoYi 规范（Entity→BO→VO→Mapper→Service→Controller），未大规模侵入 RuoYi 底层。但随着 BOM、合同、报销、AI、泛微对接等需求进来，以下五类问题会成为主要瓶颈：

1. **数据库模型偏补丁化**：BOM/合同/报销先建表但未与主链路打通，字段职责有重叠。
2. **状态机分散**：申请、验收、领用、订单、BOM 各自维护状态，缺少统一事件驱动。
3. **附件双轨制**：业务表单字段附件与 `pms_attachment` 并存，权限和检索会乱。
4. **数据权限空白**：当前全员可见，后续按项目/部门隔离成本高。
5. **流程与业务耦合**：资金扣减、库存变更、流程推进都写在 Service 事件监听里，扩展和排错困难。

结论：**不是代码乱，是业务增长速度超过了模型抽象速度。需要在继续加页面前，先确认下面几个设计决策。**

## 二、数据库设计：必须先确认的决策

### 2.1 单据主链路模型

当前核心表：

```
pms_project
  └── pms_procurement_request（申请单）
        ├── pms_procurement_request_item（申请明细）
        ├── pms_purchase_order（采购订单，目前游离）
        │     └── pms_purchase_order_item
        ├── pms_acceptance（验收单）
        │     └── pms_acceptance_item
        │           └── 驱动入库 → pms_warehouse_stock
        └── pms_issue_request（领用申请）
              └── 驱动出库 → pms_stock_movement
```

**问题**：`pms_purchase_order` 目前与申请、验收、库存都没有状态联动，几乎是独立 CRUD。后续如果采购专员要「根据申请下订单、根据订单到货验收」，订单必须被纳入主链路。

**建议方案（二选一，需要确认）**：

| 方案 | 说明 | 适合场景 |
|---|---|---|
| A. 订单并入申请 | 弱化订单概念，采购申请审批通过后直接生成/等价于订单，验收直接关联申请。 | 当前流程简单、采购即申请的组织 |
| B. 申请→订单→验收三段式 | 申请审批通过后，由采购专员/申请人转成订单；验收按订单明细验收；资金按申请扣，库存按订单/验收入。 | 有专职采购、需要分批到货、多订单对应一申请 |

**当前事实**：用户之前说过"把订单明细的采购种类移动到订单表单"，说明用户心里是把"申请"和"订单"当两个层次的。建议先按 **方案 A 的简化版** 跑通（申请即订单），但数据库保留 `pms_purchase_order` 的扩展能力，等流程稳定后再演进到方案 B。

### 2.2 状态机统一

当前状态字段混乱：

| 单据 | 状态值 | 问题 |
|---|---|---|
| 采购申请 | `draft/waiting/finish/back/cancel/invalid/termination` | 与流程状态混用 |
| 验收 | `pending/partial/finished/rejected` + 流程覆写 | 两端状态不一致 |
| 领用 | `pending/approved/rejected/issued` + 流程覆写 | 同上 |
| 订单 | `draft/ordered/partial_received/received/cancelled` | 无人更新 |

**建议**：

- 区分两类状态：
  - **业务状态**：由业务自己决定，如 `acceptance_status = none/processing/done`。
  - **流程状态**：由 Warm-Flow 决定，如 `waiting/finish/back`。
- 业务状态只给外部列表/报表用，流程推进以工作流实例状态为准。
- 建议新增一个 `pms_biz_status` 统一枚举或在各 Service 中明确"流程状态→业务状态"的映射表，避免硬编码。

### 2.3 附件存储统一

当前：

- `pms_procurement_request.payment_screenshot` / `quotation_url`
- `pms_acceptance_item.photo_url` / `invoice_url`
- 通用表 `pms_attachment(biz_type, biz_id, file_name, file_url)`

**问题**：

1. 单字段附件无法支持多张图片。
2. 审批视角查看附件需要给所有角色补 `system:oss:query` 权限，说明权限模型是按菜单权限而不是按业务 owner。
3. 后续报销打包时，需要把申请附件、验收图片、发票合并，双轨制会让聚合逻辑非常复杂。

**建议**：

- **所有附件走 `pms_attachment`**，业务表中只保留 `attachment_count` 或关键首张图缓存字段。
- `pms_attachment` 增加 `attachment_type`（如 `payment_screenshot/quotation/invoice/photo/contract`），按 `biz_type + biz_id + attachment_type` 查询。
- 权限：先维持"能查看业务单据就能看到附件"，后续若要更细，再加 `visible_role_ids` 或 `owner_id` 字段。

### 2.4 资金流水模型

当前：

- `pms_project.budget` / `used_amount`
- `pms_fund_flow` 记录流出
- 申请审批通过时双写：`used_amount++` + 插入 `pms_fund_flow`

**风险**：

1. 无冻结/占用机制：提交时只校验剩余，并发可能超支。
2. 双写无分布式事务，事件重放可能重复扣减。
3. `used_amount` 是计算冗余，与 `pms_fund_flow` 可能不一致（虽然有 `syncFromRequests` 修复工具）。

**建议**：

- 保留 `pms_fund_flow` 作为唯一资金事实来源。
- `pms_project.used_amount` 改为实时视图或定时同步，不要作为强一致性字段。
- 提交申请时做"预算占用"（新增 `pms_fund_flow` 状态：`occupied`），审批通过转 `actual`，驳回/撤销回滚。这样天然防并发超支。

### 2.5 BOM 与仓库关系

当前有三套 BOM 相关表：

- `pms_bom_catalog`：物料库（零件档案）
- `pms_bom_item`：项目级 BOM 清单
- `pms_bom_table` + `pms_bom_node`：产品 BOM 树

**问题**：三套表之间没有关联，`pms_procurement_request_item.bom_item_id` 空置。

**建议**：

- 明确三层概念：
  - **物料库（catalog）**：全公司通用零件字典，可关联仓库库存。
  - **项目 BOM（bom_item / bom_table）**：某个项目/产品由哪些零件组成。
  - **采购明细**：从 BOM 或物料库选取，生成申请。
- 建议统一用 `pms_bom_node` 树表达"项目→部件→零件"，物料库只作为节点引用（`catalog_id`）。
- 采购申请明细支持 `source_type + source_id`（来自 BOM 节点 或 物料库 或 手工），后续可追溯。

## 三、权限设计：功能权限 + 数据权限 + OSS 权限

### 3.1 功能权限（已部分实现，需补齐）

当前角色：

- `common_user`：基础面板（我的任务、采购申请/验收/领用入口）
- `team_leader`：团队上级
- `dept_leader`：部门上级
- `warehouse_admin`：仓库管理员
- `acceptance_contact`：验收对接人（当前未实际使用）

**建议**：

- 所有用户默认属于 `common_user`，保证"提交申请"这种基础功能人人可用。
- 审批节点全部绑定角色，不硬编码用户 ID。
- 超级管理员（admin）保留"代审批"能力，但要有明确日志，避免审批人以为自己没任务。

### 3.2 数据权限（当前空白，必须提前设计）

当前所有角色 `data_scope = '1'`（全部数据），Service 层未使用 `@DataScope`。

**建议的分层策略**：

| 数据类型 | 可见规则 | 实现方式 |
|---|---|---|
| 项目 | 管理员全部；项目负责人看自己负责的项目；普通用户看与自己申请/验收/领用相关的项目 | `pms_project.leader_id` + 申请/验收/领用 `create_by` |
| 采购申请 | 自己提交的、自己是审批人的、自己项目下的 | 按 `create_by` / `project_id` / 流程任务 assignee |
| 验收 | 关联到自己申请/项目的 | 按 `request_id` 反查 |
| 库存 | 仓库管理员全部；普通用户看与自己项目相关的 | 按 `project_id` 过滤 |
| 资金流水 | 管理员全部；项目负责人看本项目 | 按 `project_id` 过滤 |

**实现建议**：

- 先不过度设计，用 MyBatis-Plus 的 Wrapper 在 Service 层显式过滤，而不是一上来就加 `@DataScope` 注解（RuoYi 的数据权限注解与部门/岗位强耦合，而我们按项目过滤）。
- 每个查询接口统一加 `DataScopeUtil` 帮助类，根据当前用户角色生成 `project_id IN (...)` 条件。

### 3.3 OSS / 附件权限

当前通过给所有角色补 `system:oss:query` 解决，本质是"有菜单权限就能看所有 OSS 文件"。

**建议**：

- 短期：维持"能看单据就能看附件"，所有正常角色给 `system:oss:query`。
- 中期：OSS 文件按业务路径存储（如 `/procurement/{bizType}/{bizId}/{fileName}`），接口层校验当前用户是否有该 `biz_id` 的查看权限。
- 长期：敏感附件（合同、报价单）走独立 bucket 或预签名 URL，增加过期时间。

## 四、流程串联设计

### 4.1 当前三个流程

| 流程 | 节点 | 关键变量 |
|---|---|---|
| 采购申请 `pms_request` | start → apply → leader → gateway_amount → team_leader/dept_leader → end | `leaderId`, `amount` |
| 验收 `pms_acceptance` | start → apply → applicant → leader → team_leader → end | `applicantId`, `leaderId` |
| 领用 `pms_issue_request` | start → apply → warehouse → end | `initiator` |

### 4.2 流程间依赖

```
采购申请 finish
    ├── 资金扣减 → pms_fund_flow
    ├── 验收入口开放 → pms_procurement_request.acceptance_status = none
    │       └── 验收 finish
    │               ├── 库存入库 → pms_warehouse_stock
    │               └── 报销入口开放
    └──（可选）生成采购订单 → pms_purchase_order

库存存在
    └── 领用申请 finish
            └── 库存出库 → pms_stock_movement
```

### 4.3 流程事件与业务解耦

当前问题：资金扣减、库存变更、状态更新都直接写在 `processHandler()` 事件监听里，与流程状态强耦合。

**建议**：

- 引入领域事件：`ProcurementApprovedEvent`、`AcceptanceFinishedEvent`、`IssueApprovedEvent`。
- Service 只负责发布事件，监听者分别处理资金、库存、通知、日志。
- 这样后续加"审批通过后发邮件"、"同步泛微"、"AI 初审"都可以作为独立监听者加入，不改动 Service。

### 4.4 退回与重审

当前所有 `REJECT` 都回到 `start` 节点，实际等于终止。

**建议**：

- 采购申请：被上级驳回 → 回到申请人（可编辑后重新提交）。
- 验收：被驳回 → 回到验收发起人（可补充材料）。
- 领用：被驳回 → 回到领用人。
- 需要 Warm-Flow 节点配置 `skip_type = REJECT` 指向正确节点，而不是统一回 start。

## 五、可扩展性设计原则（后续开发必须遵守）

### 5.1 新增功能前先问四个问题

1. 这个功能属于主链路（申请→订单→验收→入库→领用）还是旁支工具（合同/报销/AI）？
2. 它的数据是新增表，还是在现有表加字段？优先扩展表，少在现有大表加字段。
3. 它要不要走工作流？要走就提前设计好节点、变量、表单路径、隐藏菜单。
4. 它会不会产生附件？产生就统一走 `pms_attachment`。

### 5.2 编码生成规则

当前按天计数，无唯一约束，高并发可能重号。

**建议**：

- 业务编码 = `模块前缀` + `日期` + `3位序号`。
- 序号生成改为数据库原子操作：用独立表 `pms_serial_number(biz_type, date, seq)`，`UPDATE ... SET seq = LAST_INSERT_ID(seq + 1)`，或直接用 Redis incr。
- 关键业务单号加唯一索引（`UNIQUE(biz_code)`），防止重号入脏数据。

### 5.3 Service 层拆分

当前 `PmsProcurementRequestServiceImpl` 已经 600+ 行，混合 CRUD、流程、资金、Excel。

**建议**：

- `PmsProcurementRequestService` 只保留 CRUD + 流程启动。
- 新建 `PmsProcurementFundService`：资金校验、占用、扣减、回滚。
- 新建 `PmsProcurementExcelService`：导出逻辑。
- 新建 `PmsProcurementFlowEventHandler`：流程事件处理。

### 5.4 库存变更必须加锁

当前 `stockInOnFinish` / `stockOutOnFinish` 先查后更新，无锁。

**建议**：

- 对 `pms_warehouse_stock` 按 `id` 使用数据库乐观锁（新增 `version` 字段）。
- 或统一走 `pms_stock_movement` 流水表，库存数量由流水汇总（事件源模式），彻底避免并发扣减问题。

| 1 | 采购申请与采购订单是否合并？ | 先合并，数据库保留扩展 | 是 |

| 6 | 流程退回是回到申请人还是终止？ | 建议回到申请人 | 是 |
| 7 | 合同、报销、AI 是否本次都进入主链路？ | 建议先作为旁支工具，不阻塞主链路 | 是 |

## 七、下一步建议动作

1. **冻结数据库大改**：在上述 7 个决策确认前，不再新增核心表字段。
2. **补齐数据权限**：即使先不过滤，也要在每个列表查询处预留 `project_id IN (...)` 的扩展点。
3. **统一附件**：新功能产生的附件必须走 `pms_attachment`，旧字段逐步迁移。
4. **事件解耦**：把 `processHandler` 里的资金、库存逻辑拆成独立监听者。
5. **加唯一索引**：给 `request_code`、`acceptance_code`、`issue_code`、`contract_no` 等加唯一索引。
6. **写状态机映射表**：明确每个流程状态变化时，业务状态如何更新。
