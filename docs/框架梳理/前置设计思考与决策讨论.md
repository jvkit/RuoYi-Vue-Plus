## 二、问题 1：采购订单是否要删除

### 2.1 现状理解

当前系统里有：

- `pms_procurement_request`（采购申请）+ `pms_procurement_request_item`（申请明细）
- `pms_purchase_order`（采购订单）+ `pms_purchase_order_item`（订单明细）
- 采购订单目前几乎是独立 CRUD，和申请、验收、库存没有联动。
- 你已经在界面上把它禁用了。

### 2.2 我的判断

**同意删除采购订单的独立页面和主链路地位。** 理由：

1. **当前业务流程不需要两层单据**：申请人提交申请 → 上级审批 → 验收 → 入库。中间不需要一个"采购专员再转一次订单"的环节。
2. **订单明细和申请明细字段高度重合**：采购种类、一级分类、二级分类、名称、规格、数量、单价、金额、供应商等，重复建模。
3. **验收直接关联申请更自然**：按采购申请一条条物料验收，用户心智最清晰。
4. **保留空跑的表和页面是负债**：后续每改一次字段都要考虑两套表，测试也要覆盖两套页面。

### 2.3 建议方案

**方案 A：彻底删除（推荐）**

- 删除前端 `views/procurement/order/` 页面。
- 删除后端 `PmsPurchaseOrder*` 相关 Controller/Service/Mapper/Entity/BO/VO/XML。
- 删除 `pms_purchase_order` / `pms_purchase_order_item` 表。
- 后续如果需要采购专员环节，直接在申请审批流里加一个"采购对接人确认"节点即可，不建新单据。

**方案 B：保留表但隐藏页面，作为未来扩展**

- 前端不显示订单菜单。
- 后端保留订单表，等以后业务需要"一申请多订单、分批到货"时再启用。

**倾向方案 A**。因为：

- "以后可能用"是过度设计，真到那天再建表也不迟。
- 当前代码里订单表没有任何实际业务规则，保留它只会增加维护成本。
- 数据库迁移时少两张表，SQL 脚本更干净。

### 2.4 风险

- 如果以后组织架构变大，出现专职采购岗位，可能需要重新引入订单层。但那时候的需求肯定和现在不一样，重新设计更合理。
- 删除前要确认没有任何 Service 引用订单表（如合同、报销目前也没引用）。

### 2.5 待确认

- [ ] 是否同意彻底删除采购订单模块（表+代码+页面）？
- [ ] 还是仅隐藏页面、保留数据库表作为占位？

## 三、问题 2：BOM、合同、报销暂时不动

### 3.1 现状理解

- `pms_bom_catalog`、`pms_bom_item`、`pms_bom_table`、`pms_bom_node` 已建表，但和采购主链路没打通。
- `pms_purchase_contract`、`pms_reimbursement` 已建表，但基本是裸 CRUD。

### 3.2 我的判断

**同意暂时不动。** 这些属于"旁支工具"，不是当前主链路的瓶颈。当前核心矛盾是：

1. 申请 → 审批 → 验收 → 入库 → 领用 要稳定。
2. 状态机、权限、流程耦合要理顺。

等主链路稳定后，再按以下顺序扩展：

1. **BOM**：先解决"项目→部件→零件"的树模型，再和采购明细打通。
2. **合同**：基于申请/验收数据自动生成合同，属于导出/文档能力。
3. **报销**：基于申请+验收+发票自动打包，属于导出/邮件能力。

### 3.3 但要先做一件事

虽然不动 BOM/合同/报销的具体功能，但要在数据库层面为它们**预留接入点**：

- 采购申请明细增加 `source_type` / `source_id` 字段，表示这条明细来自：手工添加 / BOM 节点 / 物料库。
- 验收单和申请单保持强关联，后续报销才能自动聚合。
- 附件统一走 `pms_attachment`，后续合同/报销打包时才能一键收集。

## 四、问题 3：状态机设计与项目归属

### 4.1 状态机现状

当前状态字段混乱：

| 单据 | 当前状态 | 问题 |
|---|---|---|
| 采购申请 | `draft/waiting/finish/back/cancel/invalid/termination` | 业务状态与流程状态混在一起 |
| 验收单 | `pending/partial/finished/rejected` + 流程覆写 | 流程状态覆盖业务状态 |
| 领用单 | `pending/approved/rejected/issued` + 流程覆写 | 同上 |
| 采购订单 | `draft/ordered/partial_received/received/cancelled` | 无人更新 |

### 4.2 状态机设计建议

我倾向于把状态拆成两层：

#### 第一层：流程状态（由 Warm-Flow 维护）

只关心流程实例走到哪了：

- `waiting`：待审批
- `finish`：审批通过
- `back`：被退回
- `cancel`：撤销
- `termination`：终止

流程状态存在 Warm-Flow 的 `flow_instance` 表中，业务表里的 `status` 不需要重复维护它。

#### 第二层：业务状态（由各业务表自己维护）

表达业务生命周期：

**采购申请的业务状态**：

- `draft`：草稿，未提交
- `submitted`：已提交，进入审批
- `approved`：审批通过，可进行验收
- `rejected`：被驳回，可重新编辑
- `cancelled`：申请人撤销
- `completed`：全部验收完成

**验收单的业务状态**：

- `draft`：草稿
- `submitted`：已提交
- `checking`：审批中
- `passed`：验收通过，已入库
- `rejected`：验收被驳回
- `partial`：部分通过（预留）

**领用单的业务状态**：

- `draft`
- `submitted`
- `approved`：已出库
- `rejected`

#### 映射关系

流程状态变化时，通过事件监听更新业务状态。例如：

```
流程 finish  → 采购申请 business_status = approved
流程 back    → 采购申请 business_status = rejected
流程 cancel  → 采购申请 business_status = cancelled
```

这样做的好处：

1. 列表查询、报表统计用业务状态，语义清晰。
2. 流程推进以 Warm-Flow 为准，不混乱。
3. 后续如果要接入泛微，对外暴露业务状态即可，不用暴露 Warm-Flow 内部状态。

### 4.3 项目归属字段

当前 `pms_project` 有 `dept_id` 字段，表示"归属部门"。你说"归属于部门，但是与部门无关，只是用了它的名字"，我完全理解这个痛点。

#### 问题本质

- **部门（sys_dept）**：组织人事结构，用于汇报线、数据权限、审批人查找。
- **项目归属（fund_source）**：资金来源或行政归属，如"长三角"、"天目湖"、"北京"。
- 这两者是不同维度的概念，硬塞到一个字段里会乱。

#### 建议方案

把 `pms_project` 拆成两个字段：

| 字段 | 含义 | 示例 | 用途 |
|---|---|---|---|
| `fund_source_id` | 资金来源/项目归属 | 长三角、天目湖、北京 | 资金统计、报表分组、项目前缀 |
| `dept_id` | 项目所属部门（可选） | 研发部、实验室 | 数据权限、审批人默认归属 |

新增一张字典表 `pms_fund_source`：

```sql
pms_fund_source
  - id
  - source_code    -- 编码，如 CSHJD（长三角基地）
  - source_name    -- 名称，如 长三角
  - parent_id      -- 支持层级，如长三角 → 本地隐私保护项目
  - budget         -- 总预算（可选）
  - status
```

**这样做的好处**：

1. 项目归属从部门表里解耦，不再只是"借名字"。
2. 可以做多级资金归属，如"长三角 → 本地隐私保护项目 → RAG"。
3. 项目编码可以和 `fund_source_code` 关联，如 `CSHJD-20260825-001`。
4. 后续按"资金来源"统计预算消耗更准确。

#### 另一个思路

如果部门确实不想用来管项目归属，也可以干脆：

- `dept_id` 只表示"这个项目挂在哪个部门下"（为了数据权限和审批）。
- `fund_source` 用纯文本或独立字典，不做物理外键。

我推荐第一种（独立 `pms_fund_source` 表），因为后续要按资金来源做预算和报表。

- [ ] 是否同意新增 `pms_fund_source` 表替代 `dept_id` 作为项目归属？
- [ ] 还是保留 `dept_id` 但只做部门关联，项目归属另起字段？

## 五、问题 4：权限体系设计

这是最关键的问题之一。我先分析 RuoYi 的权限机制，再给出我们的设计建议。

### 5.1 RuoYi 原生权限机制

RuoYi 的权限由这几层组成：

1. **功能权限（菜单+按钮）**
   - 通过 `sys_menu` 表的 `perms` 字段，如 `procurement:request:list`、`procurement:request:add`。
   - 通过角色 `sys_role` 分配菜单/按钮给用户。
   - 前端用 `v-hasPermi` 控制按钮显示，后端用 `@SaCheckPermission` 控制接口访问。

2. **数据权限**
   - 通过 `sys_role.data_scope` 字段控制：
     - `1`：全部数据
     - `2`：自定义数据（角色关联的部门）
     - `3`：本部门数据
     - `4`：本部门及以下数据
     - `5`：仅本人数据
     - `6`：本部门及以下或本人数据
   - 通过 `@DataScope` 注解 + MyBatis 拦截器 `PlusDataPermissionHandler` 自动拼接 SQL。
   - 但 RuoYi 的数据权限默认按 `dept_id` 过滤，我们的业务需要按 `project_id` 过滤，所以不能直接套。

3. **用户-角色-部门关系**
   - 一个用户属于一个主部门 `sys_user.dept_id`。
   - 一个用户可以关联多个角色 `sys_user_role`。
   - 一个角色可以关联多个部门（用于自定义数据权限）`sys_role_dept`。

### 5.2 我们之前的误区

你说得很对："错误在于，只有角色权限"。

当前做法：

- 创建了 `team_leader`、`dept_leader`、`warehouse_admin` 等角色。
- 把审批人硬编码或绑定到角色。
- 所有角色 `data_scope = 1`（全部数据）。

问题：

1. **数据权限缺失**：谁都能看到全部项目、全部申请、全部验收。
2. **审批人查找不灵活**：用角色可以，但不能只有角色。实际审批人应该和"项目-部门-职位"有关。
3. **普通用户权限挂得太重**：把基础功能挂到 `common_user` 角色，每次新用户都要手动关联。

### 5.3 建议的权限模型

我建议把权限分成四层，互相补充：

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：功能权限（菜单/按钮）                                      │
│  → 谁能打开哪个页面、点击哪个按钮                                  │
│  → RuoYi 原生机制：sys_menu.perms + sys_role + @SaCheckPermission │
├─────────────────────────────────────────────────────────────┤
│  第二层：数据权限（能看到哪些数据）                                 │
│  → 谁能看到哪些项目、申请、验收、库存                              │
│  → 自定义实现：按 project_id / create_by / 流程任务过滤            │
├─────────────────────────────────────────────────────────────┤
│  第三层：流程权限（能审批哪些任务）                                 │
│  → 审批节点绑定角色/部门/职位/变量                                │
│  → Warm-Flow permission_flag 支持 role:<id> / user:<id>          │
├─────────────────────────────────────────────────────────────┤
│  第四层：特殊授权（极少数例外）                                    │
│  → 直接给用户赋角色、或单独加白名单                               │
└─────────────────────────────────────────────────────────────┘
```

#### 5.3.1 功能权限

继续用 RuoYi 原生机制，但优化两点：

1. **默认角色机制**
   - 新增一个 `default_user` 角色，包含所有用户都应该有的菜单：
     - 我的任务
     - 采购申请（提交、查看自己的）
     - 采购验收（提交、查看自己的）
     - 仓库领用（提交、查看自己的）
     - 个人信息
   - 在创建用户时，自动把 `default_user` 关联给新用户。
   - RuoYi 原生没有"默认角色"，我们可以在 `SysUserServiceImpl.insertUser` 时加一个默认关联逻辑，或者写成一个 SQL 触发器。

2. **角色命名规范**
   - `default_user`：普通用户基础权限
   - `project_manager`：项目负责人（可看本项目全部数据）
   - `team_leader`：团队上级
   - `dept_leader`：部门上级
   - `warehouse_admin`：仓库管理员
   - `procurement_staff`：采购专员（如需）
   - `admin`：全部权限

#### 5.3.2 数据权限

这是我们需要自己实现的核心。建议不直接用 RuoYi 的 `@DataScope`，因为那是按部门的。我们按**项目**过滤。

**设计思路**：

每个用户能看到的数据 = 以下集合的并集：

1. **自己创建的数据**：`create_by = 当前用户ID`
2. **自己负责的项目数据**：`project_id IN (自己负责的项目)`
3. **自己审批过的数据**：通过流程任务历史查找
4. **特殊角色赋予的数据**：如仓库管理员看全部库存，admin 看全部

**实现方式**：

- 新建一个 `ProcurementDataScopeService`，根据当前用户返回可访问的 `project_id` 集合。
- 在每个列表查询的 Service 中显式拼接 Wrapper：

```java
// 伪代码
List<Long> projectIds = dataScopeService.getVisibleProjectIds();
queryWrapper.in("project_id", projectIds)
            .or().eq("create_by", currentUserId);
```

- 对于"项目负责人"这个角色，在创建/编辑项目时维护 `pms_project.leader_id`，数据权限就按 `leader_id` 查。

**关于部门权限**：

- 如果部门只是用来确定审批线，那不需要用部门过滤数据。
- 如果以后需要"部门领导看本部门全部项目"，再扩展 `pms_project.dept_id` 过滤。

#### 5.3.3 流程权限

Warm-Flow 的审批人配置支持：

- `role:<角色id>`：拥有该角色的所有用户
- `user:<用户id>`：指定用户
- `${变量名}`：流程变量，如 `${leaderId}`、`${applicantId}`

**建议**：

- 审批节点尽量绑定**角色**，不绑定具体人。
- 动态审批人（如项目负责人）用流程变量 `${leaderId}`。
- 不要在一个节点里混用多种方式，避免调试困难。

#### 5.3.4 特殊授权

对于极少数例外（如老板要看某个项目、临时工代理审批），直接：

- 给用户临时加一个角色。
- 或在项目里增加"协作人"字段，给协作人看数据权限。

不建议为了少数例外做复杂的权限引擎。

### 5.4 数据权限规则建议

| 页面 | 普通用户 | 项目负责人 | 团队/部门上级 | 仓库管理员 | admin |
|---|---|---|---|---|---|
| 项目管理 | 不可见 | 看自己的项目 | 看全部 | 不可见 | 全部 |
| 采购申请 | 看自己提交的 | 看本项目全部 | 看自己审批的 | 不可见 | 全部 |
| 采购验收 | 看自己发起的/关联申请的 | 看本项目全部 | 看审批过的 | 不可见 | 全部 |
| 仓库库存 | 看本项目库存 | 看本项目库存 | 不可见 | 全部 | 全部 |
| 领用申请 | 看自己提交的 | 看本项目全部 | 不可见 | 看全部 | 全部 |
| 资金管理 | 不可见 | 看本项目 | 不可见 | 不可见 | 全部 |

### 5.5 关于"普通用户都该有的权限挂到哪里"

你的直觉是对的：挂到 `common_user` 角色不是最优，因为每次创建用户都要手动关联。

**更优方案：默认角色**

- 新增 `default_user` 角色，包含基础菜单。
- 在 `sys_user` 新增用户时，自动关联 `default_user`。
- 这样"普通用户权限"变成系统自动赋予，不需要人工干预。

RuoYi 原生没有默认角色，但实现很简单：

```java
// 在 SysUserServiceImpl.insertUser 最后加
if (user.getRoleIds() == null || !user.getRoleIds().contains(defaultRoleId)) {
    // 自动追加 default_user
}
```

## 六、问题 5：流程与业务解耦

### 6.1 现状问题

当前代码里，流程事件监听直接处理业务：

```java
@EventListener
public void processHandler(ProcessTaskEvent event) {
    if (event.getStatus() == finish) {
        // 1. 扣减资金
        accumulateUsedAmount();
        // 2. 写资金流水
        createFundFlow();
        // 3. 更新验收标志
        updateAcceptanceStatus();
        // 4. 入库
        stockInOnFinish();
    }
}
```

问题：

1. **一个方法职责太多**：资金、库存、状态、通知全写在一起。
2. **扩展困难**：加个"审批通过后发邮件"，要改这个方法。
3. **事务边界不清**：如果资金扣减成功但入库失败，回滚范围不好控制。
4. **测试困难**：很难单独测"资金扣减"或"库存入库"。

### 6.2 建议方案：领域事件解耦

把流程事件作为触发器，发布领域事件，由专门的监听者处理各自业务。

#### 事件定义

```java
// 采购申请已通过
```

#### 这样做的好处

1. **单一职责**：每个监听者只干一件事。
2. **扩展容易**：加个"同步泛微"、"AI 初审"都是新监听者，不改动原有代码。
3. **事务清晰**：Spring 默认同步事件在发布者事务中执行，失败一起回滚。如果需要异步，加 `@Async` 和 `@TransactionalEventListener`。
4. **流程无关**：即使以后不用 Warm-Flow 了，业务逻辑也不用改，只需要换事件发布的地方。

### 6.4 关于事务一致性

如果担心事件监听失败导致数据不一致，可以：

1. **同步事件 + 同事务**：默认就是，失败一起回滚。
2. **事件表（Event Sourcing 简化版）**：把事件先写到 `pms_domain_event` 表，再由定时任务或 MQ 消费。这是最稳妥的，但复杂度也更高。
3. **关键业务直接调用**：资金扣减这种强一致性操作，可以在 Service 中直接调用 `FundService`，不通过事件。事件只用于通知、日志、弱一致业务。

我建议：

- **资金、库存** 这类强一致性操作：直接在 Service 中调用对应 Service，保证事务。
- **通知、日志、状态更新、外部同步**：用事件监听。
- 这样折中，既解耦又保证核心数据一致。
