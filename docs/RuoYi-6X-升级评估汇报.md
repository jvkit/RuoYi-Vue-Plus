# RuoYi-Vue-Plus 6.X 升级评估汇报

> 汇报对象：老板 / 产品负责人  
> 汇报人：技术部  
> 日期：2026-08-06

## 一、背景与结论

RuoYi-Vue-Plus 官方在 **2026-07-30 发布了 6.0.0 正式版**（GitHub Tag: `v6.0.0`）。当前我们本地部署的版本是 **5.6.2**，刚刚完成采购模块的重构（项目、供应商、BOM、采购申请、采购订单）。

**核心结论：建议暂缓整体升级到 6.X，优先在现有 5.6.2 上把采购业务闭环跑通；6.X 的 AI 能力可以单独调研、按需引入。**

---

## 三、6.X 最值得关注的升级：AI 模块（重点）

6.0.0 最大亮点是全面集成 **Snail AI**，并围绕 AI Agent、MCP、AI 编程做了整套扩展：

### 1. 新增 `ruoyi-snailai-server` 独立服务
- 提供企业级 AI Agent 平台整合。
- 与主应用解耦，可独立部署、独立扩容。
- 支持通过 OpenAPI 将 RuoYi 用户体系与 Snail AI 打通。

### 2. 新增 `ruoyi-ai` 模块
- 主应用内的 AI 接入层。
- 已看到 `SnailAiController`，提供 `/snail-ai/user/register` 等接口，用于将当前登录用户注册为 Snail AI OpenAPI 用户。
- 可与智能体市场联动，让业务系统直接调用 AI 能力。

### 3. 新增 `ruoyi-common-mcp` 模块
- 支持 **MCP（Model Context Protocol）服务端/客户端**。
- 这意味着 RuoYi 未来可以让大模型安全、标准化地访问系统内的数据与工具，是实现“AI 调用业务系统”的关键协议层。

### 4. 新增 AI 编程支持
- 支持 **Codex、Claude** 等 AI 编程助手接入。
- 对开发效率提升有长期价值。

### 5. Spring AI 2.0 升级
- 官方升级到 `Spring AI 2.0.0`。
- 可更方便地对接各类大模型 API、向量数据库、RAG 等场景。

## 四、6.X 对现有业务的影响

### 1. 多租户功能被移除
6.X **整体移除了多租户相关功能**。如果未来系统需要多租户，需要自行实现或评估是否接受。

### 2. 发票模块 `ruoyi-invoice` 被移除
旧版 5.6.2 中我们依赖/参考的官方 `ruoyi-invoice` 模块在 6.X 已不存在。若升级到 6.X，**发票功能需要完全自行重新开发/移植**。

### 3. 模块名变化
| 旧版 | 6.X |
|---|---|
| `ruoyi-generator` | `ruoyi-gen` |
| `ruoyi-invoice` | 已删除 |
| 无 | 新增 `ruoyi-ai` |

### 4. 代码层面变化
- 全局 `Date` 替换为 `LocalDateTime`。
- 通用 Service 接口与实体类抽离为 `ruoyi-api` 模块。
- 数据权限改为“角色 → 菜单 → 数据权限”精细化控制。
- 翻译/脱敏链路重写，使用 Jackson tree + ResponseBodyAdvice 批量翻译。
- 引入 MyBatis-Plus-Join、链式查询、聚合函数、子查询等。

这些改动意味着：**我们刚写的采购模块无法直接复制到 6.X，需要按新结构重写大量代码**。

## 五、升级成本评估

| 成本项 | 评估 |
|---|---|
| **代码移植** | 高。采购模块 controller/service/mapper/前端页面都要按 6.X 新结构调整。 |
| **发票模块** | 高。官方已删除，需自行保留/重写。 |
| **环境升级** | 中。JDK 17 → 21，MySQL 8.0 → 8.4，Redis 7 → 8，Docker 镜像全要换。 |
| **数据库脚本** | 中。6.X 表结构、字段类型有变化，菜单初始化脚本需重新核对。 |
| **测试验证** | 高。相当于在新框架上重新跑通采购、发票、审批全流程。 |
| **AI 能力引入** | 中。如果只是想用 snail-ai，6.X 提供了现成模块；但也可以独立接入。 |

**总体评估：升级不是“顺便做一下”，而是一次中等规模的重构项目。**

---

## 六、建议方案

### 方案 A（推荐）：暂缓整体升级，先跑通 5.6.2 业务
1. 继续在当前 5.6.2 上完善采购业务闭环：验收、库存、发票、付款、报销等。
2. 把现有功能稳定运行，作为生产可用版本。
3. 同时**单独调研 snail-ai / MCP / Spring AI**，评估能否以独立服务或 SDK 形式接入当前 5.6.2，不升级框架也能用上 AI 能力。
4. 等业务完整、团队有余力时，再启动向 6.X 的升级专项。

### 方案 B：直接升级到 6.X
1. 基于官方 6.X 新建分支/新目录（如 `ruoyi-6x`）。
2. 将采购模块按 6.X 结构重新移植。
3. 发票模块自行保留/重写。
4. 全量回归测试。

**风险**：周期长、Bug 多、会拖慢当前业务上线节奏。

---

## 七、给老板的决策建议

1. **短期（1-2 个月）**：不升级 6.X，专注把采购系统在 5.6.2 上跑通、跑稳。
2. **中期**：评估 snail-ai / AI Agent / MCP 对我们业务的实际价值。如果确实需要，**优先以插件/独立服务形式接入现有系统**，而非整体换框架。
3. **长期**：等团队成熟、业务稳定后，再规划 6.X 升级专项，届时采购模块已经是明确的移植范围，风险可控。
